## 图例与字段纪律

- 状态四态：**active**（可排期）｜**parked**（有重启前提未满足）｜**closed-done**（已完成销账）｜**closed-dead**（判死留痕）。
- 每条必含四要素（缺一即 FAIL）：**ID + 状态 + 重启前提 + 最后触碰波次**。
- 销账必须附**销账判据**（可执行触发条件）；未过判据不得销账。
- **维护约定（P3-④ 成文）**：新增/修订 `ModelPresets` 条目的 commit，必须**同 commit** 迁本台账
  （条数、预设 ID、状态）——B4 群发未含台账同步义务曾致 13→14 漂移五处（复审22 P3-④）。

### 收尾冻结（W90 · 2026-10-28）

- **事实**：项目已进入**首个 Release tag 前的最后一波**。tag 之后，本台账 `active` 段**不再按「每波必清」推进**，
  转为**维护态**：只处理「用户可感知的 P0/P1 + 安全/合规」两类，其余按各自状态位自然休眠。
- **不动状态位**：本次冻结**只改口径，不改任何一行的四态** —— `active` 仍是 `active`，`parked` 仍是 `parked`。
  理由：状态位是**事实描述**，冻结是**节奏**约定，两者不能混。要销账必须回源改判据，
  **不许用「冻结」当销账理由**（本仓铁律：不自行销账）。
- **唤醒条件**：`parked` 行按其「重启前提」列自然唤醒；`active` 行中属于「等设备窗口 / 等用户裁决 /
  等方案设计」的，在对应输入到位时唤醒。
- **登记纪律**：tag 后新增挂账仍按四态 + 四要素登记；**本冻结不降低登记要求，只降低清账节奏**。

## 治理注记（软守卫终态登记；W87 建立）

### 注记 1：`scripts/check-new-file-guard.sh` 的 advisory 是**终态**，不翻硬门禁（W87-19，方案 B）

- **登记结论**：`scripts/check-new-file-guard.sh`（W84-14 立、W86-05 补 `--all` 存量模式并接进 CI advisory 步骤）**永远 `exit 0`** —— 这是**终态设计**，不是「等机制稳定再说」的悬空态。此前脚本头注释写的是「等机制稳定（接入 CI、误报率归零）后再考虑升级为硬门禁」，那是一句**永远不会被执行**的毕业判据（没人定义什么叫「稳定」），与「永远 exit 1 的检查」是同一个病：没人再读它。本注记把悬空判据换成明确结论。
- **理由（本仓实测数据，不是推测）**：本仓**受行数闸门覆盖的 .kt 只有 19 个**，其余 **123 个**（≥100 行且未登记）是「**从未打算加闸门**」的常规件（UI 屏 / ViewModel / 工具类）。若把「未进 line-table」判红 ⇒ 一次性制造 **100+ 条假红**，且这些文件本来就不该有闸门 ⇒ 红灯的含义不是「有缺陷」而是「你没给这个文件加闸门」，没人会照做 ⇒ 门禁最终会被整批豁免或直接关掉。这正是 W86 `--all` 的教训（首版 206 条告警；加 ≥100 行下限后仍 123 条；最后靠 top-10 封顶才有可读性）。
- **它能抓到的真信号**：`--all` 的 **top-10 里出现「拆分产物」** —— 即本该继承母文件闸门、却因拆分脱闸的新文件（W85 的 `FileArgNormalizer.kt` / `DiagnosticsLogRow.kt` 即此型）。判读靠人，但清单已自动摆到眼前（top-10 按行数降序 + 「若它是拆分产物，必须继承母文件的闸门」的措辞）。
- **为什么不选方案 A（连续 3 波 top-10 零真信号 ⇒ 提案翻硬门禁）**：方案 A 的触发条件**不可机械判定** —— 「真信号」要人判「这是不是拆分产物」，机械面数不出来 ⇒ 会退化成「靠人记得数三波」，与本仓 G1 教训（手抄聚合面必腐）同型。**宁可诚实登记终态，也不留一个没人执行的毕业判据。**
- **翻案条件（留门，但明确门在哪）**：若将来**闸门覆盖面本身变了**（如受闸门文件从 19 个扩到覆盖全部 ≥300 行文件），「未登记 = 缺陷」才成立，那时**重开本注记**再议翻硬门禁。判据是**闸门覆盖率**，不是波数。

### 注记 2：C-2「tag 无密钥静默退 debug」= 外审处方被现役树证伪（**第 3 例**；W87 回源核实）

- **外审处方**（第四/五轮两份报告）：`release.yml` 的「Detect signing secrets」缺密钥时只打 `::notice::` 然后**静默退回 debug 签名**（`app/build.gradle.kts` 的 `signingConfig = findByName("release") ?: getByName("debug")`）⇒ 构建成功、流水线绿、产物是 debug 签名 APK。处方 = 「tag 上必须硬失败」。
- **现役树事实**：`release.yml` **早就有**这一步 —— `Gate tag release on signing secrets`（`if: startsWith(github.ref, 'refs/tags/v')`；`available != true` ⇒ `::error::` + `exit 1`），Wave4 审查 **D-P0-1** 落地，**比这两份报告都早**。两份报告**都没查到该步骤** ⇒ 处方描述的是「它以为的树」，不是现役树。
- **行为核实**：release 冒烟 run `40498254820`（`workflow_dispatch`）里该步 = **skipped**（ref 是分支 ⇒ `startsWith(refs/tags/v)` 不成立）—— 这是**期望行为**，不是门禁失效。
- **真缺陷在哪**：文件头「核心约定」原文写「缺失时打印 notice 并跳过，**绝不失败**」，与 :216 的门禁**直接冲突**。这条矛盾才是真缺陷 —— 下一个读注释的人会以为 :216 是 bug 又改回去。**W87 已订正**为两段式表述（分支/dispatch 降级 + tag 硬失败，含「debug 包无法上架、无法与正式包无缝升级、卸载重装丢历史会话」的理由），并同批订正两处同源文案：`Assemble debug APK` 的「无论有没有密钥都要有一个能装的 APK」（tag 上走不到）、`Write job summary` 的「only the debug APK was produced」（tag 上该句为假：门禁在装配之前）。
- **教训（第 3 例的共性 = 时点差）**：外审报告与现役树的**时点差**是系统性风险 —— 报告查的是它那一版的树，处方必须**回源到 tip 复核**才能采纳。前两例：① **W86 `--all` 逐条告警形态**（报告建议「逐条判红」，实测 206 条、加下限后仍 123 条 ⇒ 会制造假红潮）；② **14/14 锚点目标**（报告要求「14 条全通电」，实测 Qwen2.5 镜像体积差 8664B ⇒ **13/14** 才是正确终态，硬凑 14 会让 HF 主源下载被误拒）。
- **纪律**：采纳任何外审处方前，先 `grep` 现役树确认「这一步 / 这条判据是否已存在」。**已存在 ⇒ 缺陷降级为口径/文档订正，不新增门禁**（复制一份判据 = 两处会漂移）。

## 波末清单（每波收官必做；W87 建立）

> **为什么单独立段**：本仓的 `scripts/check-backlog-refs.sh` 有**四条 advisory**（① 候选排序 ↔ 状态位冲突、② 反向陈旧「交接说已实施但台账仍 active」、③ 申报计数骤降、④ 承接行销账「承接行已终态但源行没收」）。它们按设计**打 stderr 且不阻断**，而 arch-guard #52 的包装在脚本成功时**吞掉全部输出** ⇒ **CI 里看不见**。若不写进波末清单，这些咨询级信号会持续空转 —— 「永远不报警」与「永远报警」是同一个病：**没人再读它**。

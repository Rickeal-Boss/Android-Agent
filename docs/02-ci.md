本文说明两条工作流的设计意图、签名密钥约定，以及 CI 失败时如何定位根因。

## 0. 启用 CI 的前置条件（重要）

> **当前状态：CI 尚未启用。** 两条工作流放在 `ci-templates/`，而 GitHub 只识别 `.github/workflows/`
> 下的 YAML —— 放在 `ci-templates/` 里的只是普通文件，**不会触发任何构建**。

### 0.1 为什么要放在 `ci-templates/`

不是「不想触发 CI」，而是**推不上去**：当前两个 PAT 都**没有 `workflow` 权限**，
GitHub 会直接拒绝任何创建/更新 `.github/workflows/**` 的 push：

```
remote: error: GH013: Repository rule violations found ...
! [remote rejected] main -> main (push declined due to repository rule violations)
```

或（取决于具体配置）：

```
remote: error: refusing to allow a Personal Access Token to create or update workflow
        without 'workflow' scope
```

用 REST API 建文件同样 403。放在 `ci-templates/` 是为了让**其余代码能正常推送**，不被工作流文件卡住。

### 0.2 启用步骤

拿到有 `workflow` 权限的凭据后执行：

```bash
# 1. 拷到 GitHub 唯一识别的工作流目录
mkdir -p .github/workflows
cp ci-templates/build.yml ci-templates/release.yml .github/workflows/

# 2. 确认 ci-templates 已被清空/删除，避免留下第二份会漂移的副本
git rm -r ci-templates

# 3. 提交并推送
git add .github/workflows
git commit -m "ci: enable GitHub Actions build & release workflows"
git push
```

### 0.3 凭据需要什么权限

| PAT 类型 | 需要的权限 |
|---|---|
| **Fine-grained PAT** | 勾选 **Workflows: Read and write** |
| **Classic PAT** | 勾选 **`workflow`** scope（同时仍需 `repo`） |

只勾 `repo` / `Contents: write` **不够** —— 这是最常见的踩坑点，表现是 push 被 remote 拒绝而非报权限错。

### 0.4 单一事实来源

在 CI 真正启用之前，**`ci-templates/` 是唯一事实来源**（因为 `.github/workflows/` 推不上去）。
启用后按 §0.2 第 2 步删掉 `ci-templates/`，**不要**同时保留两份，否则日后必然出现不同步。

### 0.5 启用后怎么验证

```bash
gh workflow list                       # 应能看到 Build / Release
gh workflow run build.yml              # 先手动跑一次
gh run watch
```

若 `gh workflow list` 为空，说明文件没进 `.github/workflows/`（或被 push 拒绝了），回到 §0.2 检查。

## 1. 设计前提

三条硬约束决定了整套 CI 的形状：

| 约束 | 来源 | 对 CI 的影响 |
|---|---|---|
| 仓库没有任何 Actions variables，也没有可用的 secrets | 简报 §2 | **debug 构建必须零密钥**；release 签名只能做成「密钥存在才启用」 |
| 本地没有 JDK / Android SDK / Gradle | 简报 §6 | CI 是唯一验证通道 → 工作流必须自愈、失败日志必须可读 |
| 依赖面刻意最小化（禁注解处理器） | 简报 §6 | 依赖解析失败的概率已经很低，但仍需可诊断 |

由此得出三条设计原则：

1. **零密钥可跑通** —— `assembleDebug` 不读任何 secret，新 fork 开箱即绿。
2. **优雅降级** —— 缺密钥时 release 步骤跳过并打印 `::notice::`，**绝不失败**。
3. **自愈 + 可诊断** —— 自动接受 SDK 许可、缓存 Gradle、失败时上传 reports 与诊断快照。

## 2. 工作流一览

| 文件（启用后的位置） | 触发 | 超时 | 产物 |
|---|---|---|---|
| `.github/workflows/build.yml` | push `main` / PR → main / `workflow_dispatch` | 45 min | debug APK（30 天）；失败时 `build-reports-<sha>`（14 天） |
| `.github/workflows/release.yml` | push `UI` / tag `v*` / `workflow_dispatch` | 45 min | debug APK（30 天，保底）+ 可选签名 release APK + AAB + **R8 `mapping.txt` / `configuration.txt`**（90 天）+ GitHub Release |

> **签名断言**：release 流水线在 `assembleRelease` 之后会跑 `apksigner verify --verbose --print-certs`，
> 断言 **v2 + v3 签名方案命中** 且 **证书 DN 不含 `CN=Android Debug`**。
> 后者是防「`signing.*` 没传进 Gradle → 静默退回 debug 签名」这一失败模式的关键闸门
> （`app/build.gradle.kts` 的兜底分支会让它悄无声息地发生）。
>
> **产物上传策略**：release artifact 用 `if-no-files-found: error`（旧版是 `warn`，
> 曾把「`bundle/release/*.aab` 从未生成」掩盖成静默成功）。

> ⚠️ **启用前，这两份文件的实际位置是 `ci-templates/build.yml` / `ci-templates/release.yml`。**
> 迁移步骤与凭据权限要求见 [§0 启用 CI 的前置条件](#0-启用-ci-的前置条件重要)。

两者共享同一套「环境准备」步骤序列：

```
checkout → setup-java (temurin 21) → 引导 Android SDK 并接受许可
        → 安装 .github/ci-gradle.properties → gradle/actions/setup-gradle
        → 解析启动器 → 验证 Gradle → 构建 → 上传产物 / 上传报告
```

## 3. `build.yml` 详解

### 3.1 触发与并发

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

PR 上取消在途任务（省额度、反馈更快），`main` 上**不取消**——保证每个提交的构建结论都是完整可追溯的。
`permissions: contents: read` 遵循最小权限。

### 3.2 工具链

- `actions/checkout@v4`
- `actions/setup-java@v5`：`distribution: temurin`、`java-version: 21`。
  **故意不开 `cache: gradle`**——Gradle 缓存统一交给 `gradle/actions/setup-gradle`，两套缓存并存会互相污染。
  > 版本说明：上游 `actions/setup-java` 的 **v1–v4 已标记废弃**，v5（v5.7.0）与 v6 均可用。
  > 本项目用 **v5**。若某天 v5 也废弃，改 tag 即可，输入参数（`distribution` / `java-version`）不变。
- `gradle/actions/setup-gradle@v6`：负责 Gradle User Home 的缓存，以及（本项目的关键）安装 Gradle。
  - `gradle-version: '9.7.1'` —— **引号必需**，否则 YAML 会把它解析成非法数字。
    上游对「没有 wrapper 的项目」的官方写法就是 `gradle-version` + 直接调 `gradle`：
    「The setup-gradle action can download and install a specified Gradle version,
    adding this installed version to the PATH.」
  - `validate-wrappers: false` —— 该 action **默认会做 wrapper 校验**（比对 `gradle-wrapper.jar`
    的已知校验和）。CI 根本不执行 wrapper，这个校验对我们是纯粹的额外失败面，显式关掉。
    （仓库里的 jar 是从 `gradle/gradle` 官方仓库 `v9.7.1` tag 取的原版，已核对 sha256 与
     34 个条目，本身可信；关掉是「不用就别校验」，不是因为它可疑。）
    > ⚠️ **若将来把 CI 改回 `./gradlew`，必须把它翻回 `true`** —— 那时 wrapper 会被真正执行，
    > 校验才有意义。这个开关与「是否使用 wrapper」是绑定的，不要孤立地改其中一个。
  - `cache-cleanup: on-success` —— v6 起参数改名为 `cache-cleanup`
    （v3/v4 叫 `gradle-home-cache-cleanup`）。`on-success` 表示仅构建成功时清理，
    失败时保留 Gradle User Home 便于排查。
  - `add-job-summary: 'on-failure'` —— 失败时输出缓存命中报告。
- `actions/setup-java@v5`：**不要用 v1–v4，上游已废弃**；v5.7.0 与 v6 均可用，本项目用 v5。
  另外 **故意不开 `cache: gradle`** —— 上游明确说明 `setup-java` 的 Gradle 缓存会与 `setup-gradle`
  互相干扰，所以缓存统一交给 `setup-gradle`。
- `actions/checkout@v6`：上游当前示例统一使用 v6。

### 缓存 Provider（许可考量）

`setup-gradle` v6 有两种缓存实现，通过 `cache-provider` 选择：

| Provider | 许可 | 说明 |
|---|---|---|
| `enhanced`（**默认**） | 闭源商业库 `gradle-actions-caching` | **对 public 仓库免费**；细粒度条目、去重、智能清理，更快 |
| `basic` | MIT（`@actions/cache` 封装） | 全链路开源；无去重/清理，缓存体积更大、首次更慢 |

本项目是 **public + Apache-2.0**，两者都合规。**当前保持默认 `enhanced`**。
若后续要求全链路 MIT，加一行 `cache-provider: basic` 即可，代价是缓存体积和首构建时间。

### 3.2.1 Gradle 启动器解析：默认用 `gradle`，不用 `./gradlew`

**结论先行：CI 一律用 `gradle`，不用 `./gradlew`。**

**先澄清一个事实**：仓库里的 wrapper 是**完整且可信**的——
`gradle-wrapper.jar` 取自 [`gradle/gradle` 官方仓库 `v9.7.1` tag](
https://raw.githubusercontent.com/gradle/gradle/v9.7.1/gradle/wrapper/gradle-wrapper.jar)，
`gradle-wrapper.properties` 的 `distributionUrl` 指向 `gradle-9.7.1-bin.zip`。
**本地开发者可以直接 `./gradlew` 构建**（有 JDK 即可），wrapper 保留在仓库里正是为了这一点。

CI 仍然选择 `gradle` 而非 `./gradlew`，理由是**控制失败面，而不是不信任 wrapper**：

- 走 wrapper 会多引入两个变量：`gradle-wrapper.jar` 能否正常执行、
  以及构建时能否联网下载 `gradle-9.7.1-bin.zip`。这两者都不是 CI 必需的。
- `gradle-version: '9.7.1'` 由 `setup-gradle` 下载官方分发并写入 PATH，
  版本被**显式钉死**，行为可预期，且与 wrapper 声明的版本完全一致。
- 两条路径产出同一版本（9.7.1），所以这个选择没有功能差异，纯粹是可靠性取舍。

两条工作流都有一个 `Resolve Gradle launcher` 步骤，**只做确认、不做兜底**：

```bash
if ! command -v gradle > /dev/null 2>&1; then
  echo "::error::'gradle' is not on PATH — setup-gradle failed to install it."; exit 1
fi
echo "GRADLE_CMD=gradle" >> "$GITHUB_ENV"
```

**刻意不留 `./gradlew` 兜底分支**：兜底本意是提高可用性，但它会让
「`gradle` 装不上」这个**清晰的错误**退化成「wrapper 执行失败」这种**难定位的错误**。
`setup-gradle` 已保证 PATH 上有 Gradle，兜底没有收益，删掉最干净。

后续所有构建步骤统一用 `"$GRADLE_CMD"`。

> 若要改回 wrapper：只需把这一行改成 `echo "GRADLE_CMD=./gradlew" >> "$GITHUB_ENV"`，
> **不需要改动任何构建步骤**。仓库的 wrapper 本身可直接用。

### 3.2.2 模块级验证（开荒期专用）

开荒期模块是逐个落地的（`core-model` → `core-engine` → `core-agent`/`core-data` → `core-design` → `feature-*` → `app`），
在 `:app` 还不存在时跑 `:app:assembleDebug` 必然失败。

因此 `workflow_dispatch` 提供了 `gradle_task` 输入：

```bash
gh workflow run build.yml -f gradle_task=":core-model:assembleDebug"
```

- 默认 `:app:assembleDebug`；留空也走默认值。
- 输入值会被插值进 shell，因此做了**白名单校验**（只允许 `[A-Za-z0-9_:.-]`），非法值直接报错退出。
- library 模块产出的是 `.aar` 不是 `.apk`：此时跳过 APK 上传，改传 `**/build/outputs/aar/*.aar`；
  只有默认任务 `:app:assembleDebug` 没产出 APK 才算真失败。
- **也支持非打包任务**，例如 `buildEnvironment`——它不产出任何文件，
  上面的逻辑会打印一条 `::notice::` 并跳过上传，**不会失败**。
  排查 KGP 版本时很有用（见 §5.2-C）。

建议每完成 1~2 个模块就用这种方式推一次 CI，别攒到最后。

**冒烟顺序：按风险从高到低，而不是按模块编号**

```bash
gh workflow run build.yml -f gradle_task=":core-design:assembleDebug"   # 1. Compose 编译器链路（风险最高，一次覆盖 R2+R16）
gh workflow run build.yml -f gradle_task=":core-engine:assembleDebug"   # 2. litertlm 0.11.0 API 漂移（次高）
gh workflow run build.yml -f gradle_task=":core-model:assembleDebug"    # 3. 基础：serialization 插件
gh workflow run build.yml -f gradle_task=":app:assembleDebug"           # 4. 最后才是整体
```

**为什么先跑 `:core-design`**：KGP 版本不匹配（R16）与 Compose BOM × 内置 Kotlin（R2）
其实是**同一个失败面**——都是 Compose 编译器插件与 KGP 对不上，会被同一次编译同时暴露。
先跑它能一次结掉两个最高风险项，不必分开跑两次。

### 3.2.3 回退路径与爆炸半径

> ⚠️ **本节关于 Kotlin 的部分已于 2026-09-18 修正。** 早期版本写的是「把
> `libs.versions.toml` 的 `kotlin` 一行从 2.3.0 改成 2.2.21」——**这条在 AGP 9 下是错的**，
> 已作废。原因见下方，正确做法见 [§5.2-C](#c-compose-编译器与-kotlin-版本不匹配)。

| 风险 | 正确回退动作 | 爆炸半径 |
|---|---|---|
| Compose 编译器 × Kotlin 不匹配 | **不要改 catalog 的 `kotlin`**（见下）。先用 `buildEnvironment` 实测 AGP 实际解析到的 KGP 版本，再按报错给出的版本在顶层 build 文件用 `buildscript { dependencies { classpath("org.jetbrains.kotlin:kotlin-gradle-plugin:<版本>") } }` 声明 | 顶层 build 文件一处（或 AGP 版本一处） |
| litertlm 0.11.0 API 漂移 | 按架构文档 §0.1 的标注摘除对应文件 | **一个文件**（`LiteRtLmEngine.kt`），其余模块不受影响 |

#### 为什么「改 catalog 一行降 Kotlin」行不通

AGP 9.0 起对 Kotlin Gradle 插件 (KGP) 有**运行时依赖**（AGP 9.0 → KGP 2.2.10）：

> AGP 9.0 现在对 Kotlin Gradle 插件 **2.2.10** 具有运行时依赖关系。这意味着您不再需要声明
> KGP 版本，并且**如果您使用的 KGP 版本低于 2.2.10，Gradle 会自动将您的 KGP 版本升级到 2.2.10**。

再叠加「AGP 9 禁止显式应用 `org.jetbrains.kotlin.android`」，结论是：

- **Kotlin 版本由 AGP 决定，不再由我们的 version catalog 决定。** 改 `kotlin = "2.2.21"` 改不动 KGP。
- 想用**更高**的 Kotlin：官方做法是在**顶层** build 文件加 `buildscript { dependencies { classpath(...) } }`。
- 想**降级**：必须先 opt-out 内置 Kotlin —— `gradle.properties` 加
  `android.builtInKotlin=false` **且** `android.newDsl=false`（两个必须同时设）；
  最低只能降到 2.0.0，且 **AGP 10.0 会移除该开关**，只作临时逃生舱。

不要一次改多个变量，否则无法归因。

### 3.2.4 已排除项（已核对 AGP 9.3.0 RN，不会成为 CI 失败原因）

排查时可以**直接跳过**这几项，避免浪费时间：

| 项 | AGP 9.3 要求 | 本项目 | 结论 |
|---|---|---|---|
| Gradle 最低 / 默认 | 9.5.0 | 9.7.1 | ✅ 通过 |
| JDK 最低 / 默认 | 17 | CI 21 | ✅ 通过 |
| SDK Build Tools | 36.0.0 | 36 | ✅ 通过 |
| 支持的最高 API | 37 | compileSdk 36 | ✅ 通过 |
| ProGuard DSL | AGP 9.3 新增 `optimization { enable = true }`，但 legacy DSL（`isMinifyEnabled` + `proguardFiles`）**继续受支持** | 用 legacy | ✅ 不用改 |

> ⚠️ **AGP 9.3 与 Kotlin 相关的两个坑，记住以免误判：**
> 1. AGP 9.3.x RN 的兼容性表**没有 KGP 行**（只有 AGP 9.0 才写了 KGP 2.2.10）。想查「AGP 9.3.2 内置哪个 Kotlin」查不到，只能实测 `buildEnvironment`。
> 2. AGP 9.3.2 修过一个 bug：**lint 在 JDK 17 上崩**（`NoSuchMethodError: List.removeLast()`）。
>    我们用 JDK 21 不受影响，且 `assembleDebug` 不跑 lint；
>    **但若将来给 CI 加 lint 步骤，要留意 JDK 版本**。

### 3.3 Android SDK 许可自愈

AGP 9 会自动下载缺失的 platform / build-tools（`android.builder.sdkDownload=true`），
但**许可证未接受会让下载直接失败**。所以工作流在运行构建之前先把许可哈希写进 SDK 根目录：

```bash
mkdir -p "$sdk_root/licenses"
printf '%s\n%s\n' \
  '24333f8a63b6825ea9c5514f83c2829b004d1fee' \
  '8933bad161af4178b1185d1a37fbf41ea5269c55' \
  > "$sdk_root/licenses/android-sdk-license"
# ... android-sdk-preview-license / intel-android-extra-license / android-googletv-license
```

SDK 根目录按 `ANDROID_HOME` → `$HOME/android-sdk` → `/usr/local/lib/android/sdk` → … 顺序探测，
若镜像里带 `cmdline-tools` 再补跑一次 `sdkmanager --licenses` 兜底。

### 3.4 CI Gradle 属性

`.github/ci-gradle.properties` 被复制到 `~/.gradle/gradle.properties`。
**用户级 properties 优先级高于项目级**，所以它只放「构建环境」相关开关，不碰依赖版本与 SDK 版本：

| 键 | 值 | 取舍理由 |
|---|---|---|
| `org.gradle.jvmargs` | `-Xmx4g -XX:MaxMetaspaceSize=1g -Dfile.encoding=UTF-8` | runner 约 4 vCPU / 16 GB，留足余量给 Kotlin 编译进程 |
| `org.gradle.daemon` | `false` | CI 一次性任务，避免常驻进程与锁竞争 |
| `org.gradle.parallel` | `true` | 多模块并行；代价是日志交错，可接受 |
| `org.gradle.configuration-cache` | **`false`** | AGP 9 + Compose 编译器组合下配置缓存行为不确定；**正确性优先于几十秒速度**，稳定后可再试 |
| `org.gradle.caching` | `true` | task 级构建缓存，由 setup-gradle 持久化 |
| `kotlin.incremental` | `false` | CI 每次全新 checkout，增量无意义且偶发状态不一致 |
| `android.builder.sdkDownload` | `true` | 允许自动下载 compileSdk 36 组件 |
| `android.nonTransitiveRClass` | `true` | AGP 8+ 默认值，显式声明保证本地/CI 一致 |
| `android.nonFinalResIds` | `true` | AGP 8+ 默认值 |
| `android.useAndroidX` | `true` | 无 legacy support 依赖 |

命令行还额外传了 `-Dorg.gradle.jvmargs=...`（优先级最高），与文件同值，做双保险。

### 3.5 构建与产物

```bash
"$GRADLE_CMD" --no-daemon --stacktrace -Dorg.gradle.jvmargs=... "$GRADLE_TASK"
```

- **只跑 assembleDebug，不跑 lint / test**。开荒阶段 lint 规则不稳定，跑它会引入与「能否编译」无关的噪音。
  后续若要加 lint，应作为**独立 job** 而非塞进主构建。
- 先单独跑 `"$GRADLE_CMD" --version` 验证工具链，把「Gradle 装不起来」和「源码编译失败」两类问题分开。
- 成功后校验 APK 真实存在再上传（`if-no-files-found: error`），避免空产物被当成成功。
- 失败时上传 `**/build/reports/**`、`**/build/outputs/logs/**`，
  并额外打印 JDK 版本、SDK 已装 platform / build-tools 列表。
- **CI 绝不下载模型**：4B 模型 > 2GB，模型由用户自行导入（架构文档 §0.3）。
  工作流里没有任何拉取 `.litertlm` / `.task` 的步骤，也不要加。

## 4. `release.yml`：可选签名

### 4.1 密钥约定

四个 secrets，**全部可选**：

| Secret | 含义 | 获取方式 |
|---|---|---|
| `SIGNING_KEYSTORE_BASE64` | keystore 文件的 base64 | `openssl base64 -A -in liquidagent.jks` |
| `SIGNING_KEYSTORE_PASSWORD` | keystore 密码 | |
| `SIGNING_KEY_ALIAS` | key alias | `keytool -list -v -keystore liquidagent.jks` |
| `SIGNING_KEY_PASSWORD` | key 密码 | |

### 4.2 为什么用 step outputs 而不是 `if: secrets.X != ''`

`secrets` 上下文在步骤级 `if` 表达式中的可用性并不可靠，因此这里用 shell 探测后写入 outputs：

```yaml
- name: Detect signing secrets
  id: signing
  env:
    KS_B64: ${{ secrets.SIGNING_KEYSTORE_BASE64 }}
    # ...
  run: |
    if [ -n "${KS_B64:-}" ] && ... ; then
      echo "available=true"  >> "$GITHUB_OUTPUT"
    else
      echo "available=false" >> "$GITHUB_OUTPUT"
      echo "::notice::Signing secrets NOT configured ..."
    fi
```

后续步骤用 `if: steps.signing.outputs.available == 'true'` 做门禁。
**四个 secret 缺任何一个都整体降级**，避免出现「有 keystore 没密码」的半配置状态。

### 4.3 降级路径

```
assembleDebug          → 无条件执行，永远有一个能装的 APK
  ↓
Detect signing secrets → available=false 时：跳过 decode keystore / assembleRelease / gh-release
  ↓
Publish GitHub Release → 仅在 refs/tags/v* 且 assembleRelease 成功时执行
```

### 4.4 `-P` 属性名（**给开发同事的硬性约定**）

CI 通过 `-P` 传入：

```bash
./gradlew :app:assembleRelease \
  -Psigning.storeFile=/path/to/liquidagent-release.jks \
  -Psigning.storePassword=*** \
  -Psigning.keyAlias=*** \
  -Psigning.keyPassword=***
```

`app/build.gradle.kts` 必须实现如下逻辑：

```kotlin
// 伪代码，示意约定
val storeFilePath = project.findProperty("signing.storeFile")?.toString()
if (storeFilePath != null && File(storeFilePath).exists()) {
    signingConfigs.create("release") {
        storeFile = file(storeFilePath)
        storePassword = project.findProperty("signing.storePassword")?.toString()
        keyAlias     = project.findProperty("signing.keyAlias")?.toString()
        keyPassword  = project.findProperty("signing.keyPassword")?.toString()
    }
    buildTypes.getByName("release") { signingConfig = signingConfigs.getByName("release") }
} else {
    // 无签名配置：release 退回 debug 签名，保证 assembleRelease 仍然可跑通
}
```

要点：

1. **属性名固定为** `signing.storeFile` / `signing.storePassword` / `signing.keyAlias` / `signing.keyPassword`。
2. 用 `findProperty`（返回 `null`）而不是 `property`（缺失会抛异常）。
3. **release 构建类型必须始终存在**，只是签名配置可选——否则无密钥时 `assembleRelease` 会因找不到 build type 而失败。
4. 降档时退回 debug 签名即可，AGP 允许这种配置；产物不能上架，但 CI 能跑绿。

## 5. 排障手册

### 5.1 先做这三件事

1. 打开失败 run 的 **Annotations** 面板 —— `::error::` / `::warning::` 会直接钉在具体步骤上。
2. 下载 `build-reports-<sha>` artifact，看 `**/build/reports/**` 下的 HTML 报告。
3. 展开失败步骤的日志，找第一个 `What went wrong:`（Gradle 的真因永远在它下面，`Caused by:` 是更深层原因）。

> 不要只看最后一段日志。Gradle 的错误摘要在末尾，但真正的根因通常在
> `Execution failed for task ':app:xxx'` 之后紧跟的 `> ` 缩进块里。

### 5.2 常见失败与处理

#### A. SDK 许可 / 平台下载失败

```
Failed to install the following Android SDK packages as some licences have not been accepted.
```

或

```
Could not determine the dependencies of task ':app:compileDebugJavaWithJavac'.
> Failed to find Build Tools revision 36.x
```

**处理**：确认 `Bootstrap Android SDK and accept licenses` 步骤跑过，且 `ANDROID_HOME` 指向真实存在的目录。
如果 runner 镜像换了路径导致探测失败，在日志里看 `::notice::Android SDK root = ...` 确认。
许可证哈希若被 Google 更新，需要同步改 `build.yml` / `release.yml` 里的哈希列表。

#### B. 依赖解析失败

```
Could not resolve com.google.ai.edge.litertlm:litertlm-android:0.11.0
```

**处理**：
1. 先确认坐标与版本 —— `litertlm-android` 是 `com.google.ai.edge.litertlm` 组下的产物，
   与 `com.google.mediapipe:tasks-genai` 和 `com.google.ai.edge:litertlm` 都不同（见简报 §3）。
2. 确认 `settings.gradle.kts` 的 `dependencyResolutionManagement` 里包含 `google()` 与 `mavenCentral()`。
3. 若该版本在 Google Maven 上不可达，说明已下架 —— 需要改版本，**不要**私自升到 0.17.x，先同步给主理人。

#### C. Compose 编译器与 Kotlin 版本不匹配

```
This version (x.y.z) of the Compose Compiler requires Kotlin version a.b.c but you appear to be using Kotlin version d.e.f
```

或类似的 `IllegalArgumentException: No value passed for parameter` / 编译期崩溃。

**处理**：

> ⚠️ **简报 §4 写的「把 Kotlin 降到 2.2.21」在 AGP 9 下已失效，不要执行。**
> AGP 9 内置 Kotlin，KGP 版本由 AGP 决定，改 `gradle/libs.versions.toml` 的 `kotlin` 一行**无效**。
> 背景见 §3.2.3。

1. **先实测出 AGP 实际解析到的 KGP 版本**（这比查文档准）：
   ```bash
   # CI 上（gradle_task 输入支持纯任务名）
   gh workflow run build.yml -f gradle_task="buildEnvironment"
   # 本地
   gradle buildEnvironment
   # 或只看 classpath
   gradle :core-design:dependencies --configuration classpath
   ```
   在输出里找 `org.jetbrains.kotlin:kotlin-gradle-plugin:<版本>`，这就是 AGP 9.3.2 实际用的 KGP。
   > ⚠️ **不要去查 AGP 9.3.x Release Notes 的「兼容性」表想找 KGP 行——那张表只有
   > Gradle / SDK Build Tools / NDK / JDK 四项，没有 KGP 行**（只有 AGP 9.0 那版才写了 KGP 2.2.10）。
   > 查文档这条路走不通，实测是唯一可靠办法。
2. **若报错信息本身给出了期望版本**，以它为准。
3. **声明更高版本的 KGP**（官方指定做法）：在**顶层** `build.gradle.kts` 加
   ```kotlin
   buildscript {
       dependencies { classpath("org.jetbrains.kotlin:kotlin-gradle-plugin:<版本>") }
   }
   ```
   版本取第 1 步实测值或第 2 步报错给出的值。
4. **仍需降级时的逃生舱**：`gradle.properties` 加
   ```
   android.builtInKotlin=false
   android.newDsl=false
   ```
   两个**必须同时设**；最低只能降到 Kotlin 2.0.0；**AGP 10.0 会移除该开关**，只作临时手段。
5. **最后才考虑降 Compose BOM**（退到 gallery 验证过的版本）。
6. 每一步都单独提交、单独看 CI 结果，不要一次改两个变量，否则无法归因。

> 已知高风险点：Compose BOM `2026.02.00` 与 AGP 9.3.2 内置 KGP 的组合未在同一仓库验证过
> （gallery 用的是 Kotlin 2.2.21）。所以这条路径**很可能会被走到**，按上面顺序处理即可。
>
> **省一次 CI**：R16（KGP 版本与 catalog 不匹配）和 R2（Compose BOM × 内置 Kotlin）
> 其实是**同一个失败面**——都是 Compose 编译器插件与 KGP 对不上，会被同一次编译同时暴露。
> 所以只需跑一次 `:core-design:assembleDebug`，不必为两项分开跑。

#### D. AGP 9 DSL 写法问题

```
Unresolved reference: compileSdk
```

**处理**：AGP 9.x 用块式 DSL：

```kotlin
android {
    compileSdk { version = release(36) }
}
```

简报 §4 已明确：`compileSdk 36 / targetSdk 36 / minSdk 31`。

#### E. 内存 / GC 相关

```
OutOfMemoryError / GC overhead limit exceeded / Could not reserve enough space for object heap
```

**处理**：调 `.github/ci-gradle.properties` 里的 `org.gradle.jvmargs`。
runner 是 4 vCPU / 16 GB，`-Xmx4g` 已经偏保守；如果仍 OOM，说明可能有依赖把整个模型文件读进内存，先查代码而不是继续加内存。

#### F. 配置缓存相关

```
Configuration cache state could not be cached: ...
```

**处理**：CI 已显式 `org.gradle.configuration-cache=false`。如果还在报，说明项目级 `gradle.properties`
里没有覆盖成功——检查 `Install CI Gradle properties` 步骤的 `::group::` 输出，确认文件确实写进去了。

#### G. Gradle 装不上 / wrapper 相关报错

```
Error: 'gradle' is not on PATH — gradle/actions/setup-gradle failed to install it.
```

或

```
Could not open ... gradle-wrapper.jar
Error: Could not find or load main class org.gradle.wrapper.GradleWrapperMain
```

**处理**：CI **完全不走 wrapper**（见 §3.2.1），所以 wrapper 类报错只可能是
`setup-gradle` 没装上 Gradle，或者 `validate-wrappers` 校验报了错。

排查顺序：

1. 看 `Resolve Gradle launcher` 步骤日志：正常应是 `::notice::Using Gradle installed by ...` 加版本号。
2. 若失败，检查 `Set up Gradle` 步骤日志 —— 大概率是 `gradle-version: '9.7.1'` 分发下载失败，
   或该 action 的输入名又变了（v4→v6 就把 `gradle-home-cache-cleanup` 改成了 `cache-cleanup`）。
3. 若报错来自 `validate-wrappers`：确认已设置 `validate-wrappers: false`。
   CI 不执行 wrapper，这个校验对我们只是额外失败面。

> **关于 `gradle-wrapper.jar`**：它是从 `gradle/gradle` 官方仓库 `v9.7.1` tag 取的原版，
> **不要删除**——保留它，任何有 JDK 的人都能 `./gradlew` 本地构建。
> `.gitignore` 里的 `!gradle-wrapper.jar` 是必要的放行，不是遗留问题。

#### H. Action 版本无法解析

```
Unable to resolve action `actions/setup-java@v5`, unable to find version `v5`
```

**处理**：改 tag 即可，输入参数基本不用动。当前版本矩阵（已核对上游文档）：

| Action | 本项目 | 备注 |
|---|---|---|
| `actions/checkout` | **v6** | 上游当前示例统一 v6 |
| `actions/setup-java` | **v5** | v5.7.0 与 v6 可用；**v1–v4 已废弃** |
| `gradle/actions/setup-gradle` | **v6** | v6 才有 `cache-provider`；注意 `cache-cleanup` 是 v6 的新参数名 |
| `actions/upload-artifact` | v4 | |
| `softprops/action-gh-release` | v2 | |

#### I. 首次构建特别慢 / 超时

`litertlm-android` 是个不小的 AAR，首次构建需要下载并解压，**10 分钟量级属正常**。
`timeout-minutes: 45` 留了充足余量；后续构建命中 `setup-gradle` 的依赖缓存后会快很多。

若仍超时：看 `Set up Gradle` 的 job summary 确认缓存是否命中；
缓存未命中通常是 `gradle/libs.versions.toml` 又变了（缓存 key 与依赖版本相关）。

### 5.3 优化项（后续可做）

| 项 | 收益 | 前置条件 |
|---|---|---|
| 拆出独立的 `lint` / `test` job 并与主构建并行 | 主构建反馈更快，lint 失败不阻塞 APK 产出 | 构建稳定后 |
| 开启 `org.gradle.configuration-cache=true` | 二次构建显著提速 | AGP 9 + Compose 组合验证通过 |
| PR 上按 changed paths 过滤（非 Android 文件改动跳过构建） | 省 CI 额度 | 需要稳定的 path filter |
| 增加 `macos-latest` runner 做交叉验证 | 发现平台相关问题 | 当前 runner 时长翻倍，暂不划算 |
| 上传 APK 到 PR 评论 / 分发平台 |  reviewers 直接装包 | 需要额外 token，**零密钥约束下暂缓** |

## 6. 本地没有 JDK 也能改 CI

修改工作流后，用 CLI 触发并观察：

```bash
gh workflow run build.yml --ref <branch>
gh run watch            # 实时跟踪
gh run view --log-failed  # 只看失败步骤的日志
```

YAML 语法可以在提交前用任一 YAML 解析器粗验（CI 本身也会在解析失败时立刻报错，成本很低）。

# 02 · CI 设计与排障手册

> 维护人：崔续程（CI 工作流专家）
> 事实基线：[`00-recon-brief.md`](00-recon-brief.md)

本文说明两条工作流的设计意图、签名密钥约定，以及 CI 失败时如何定位根因。

---

## 1. 设计前提

三条硬约束决定了整套 CI 的形状：

| 约束 | 来源 | 对 CI 的影响 |
|---|---|---|
| 仓库没有任何 Actions variables，也没有可用的 secrets | 简报 §2 | **debug 构建必须零密钥**；release 签名只能做成「密钥存在才启用」 |
| 本地没有 JDK / Android SDK / Gradle | 简报 §6 | CI 是唯一验证通道 → 工作流必须自愈、失败日志必须可读 |
| 依赖面刻意最小化（禁注解处理器） | 简报 §6 | 依赖解析失败的概率已经很低，但仍需可诊断 |

由此得出三条设计原则：

1. **零密钥可跑通** —— `assembleDebug` 不读任何 secret，新 fork 开箱即绿。
2. **优雅降级** —— 缺密钥时 release 步骤跳过并打印 `::notice::`，**绝不失败**。
3. **自愈 + 可诊断** —— 自动接受 SDK 许可、缓存 Gradle、失败时上传 reports 与诊断快照。

## 2. 工作流一览

| 文件 | 触发 | 超时 | 产物 |
|---|---|---|---|
| `.github/workflows/build.yml` | push `main` / PR → main / `workflow_dispatch` | 45 min | debug APK（30 天）；失败时 `build-reports-<sha>`（14 天） |
| `.github/workflows/release.yml` | push tag `v*` / `workflow_dispatch` | 45 min | debug APK（30 天，保底）+ 可选签名 release APK/AAB（90 天）+ GitHub Release |

两者共享同一套「环境准备」步骤序列：

```
checkout → setup-java (temurin 21) → 引导 Android SDK 并接受许可
        → 安装 .github/ci-gradle.properties → gradle/actions/setup-gradle
        → 验证 wrapper → 构建 → 上传产物 / 上传报告
```

## 3. `build.yml` 详解

### 3.1 触发与并发

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

PR 上取消在途任务（省额度、反馈更快），`main` 上**不取消**——保证每个提交的构建结论都是完整可追溯的。
`permissions: contents: read` 遵循最小权限。

### 3.2 工具链

- `actions/checkout@v4`
- `actions/setup-java@v5`：`distribution: temurin`、`java-version: 21`。
  **故意不开 `cache: gradle`**——Gradle 缓存统一交给 `gradle/actions/setup-gradle`，两套缓存并存会互相污染。
  > 版本说明：上游 `actions/setup-java` 的 **v1–v4 已标记废弃**，v5（v5.7.0）与 v6 均可用。
  > 本项目用 **v5**。若某天 v5 也废弃，改 tag 即可，输入参数（`distribution` / `java-version`）不变。
- `gradle/actions/setup-gradle@v4`：负责 `~/.gradle/caches` 与 `~/.gradle/wrapper` 的缓存，
  `gradle-home-cache-cleanup: true` 避免缓存无限膨胀，
  `add-job-summary: 'on-failure'` 在失败时给出缓存命中情况。
  另外显式传了 **`gradle-version: '9.7.1'`** —— 仓库可能没有 wrapper（见架构文档 §1.2），
  指定版本可保证 PATH 上始终有一个正确版本的 `gradle`。

### 3.2.1 Gradle 启动器解析：默认用 `gradle`，不用 `./gradlew`

**结论先行：CI 一律用 `gradle`，不用 `./gradlew`。**

理由（架构文档 §1.2：本地没有 Gradle，wrapper jar 需要由 Gradle 自身生成）：

- 仓库里的 `gradlew` / `gradle-wrapper.jar` / `gradle-wrapper.properties` 都是**无本地 Gradle 的环境下手工拼出来的**，
  二进制 jar 的完整性无法在本地验证。把它当作 CI 的单点依赖风险太高。
- 由 `gradle/actions/setup-gradle` 显式安装 **Gradle 9.7.1** 是最确定的路径：
  直接下载官方分发，不依赖仓库里任何二进制文件。
- 版本一致性已核对：`gradle-wrapper.properties` 里的 `distributionUrl` 同样指向
  `gradle-9.7.1-bin.zip`，与 `gradle-version: '9.7.1'` **完全一致**，两条路径行为等价。

两条工作流都有 `Resolve Gradle launcher` 步骤：

```bash
if command -v gradle > /dev/null 2>&1; then
  echo "GRADLE_CMD=gradle" >> "$GITHUB_ENV"          # 默认路径
elif [ -f ./gradlew ] && [ -f gradle/wrapper/gradle-wrapper.properties ] && [ -f gradle/wrapper/gradle-wrapper.jar ]; then
  chmod +x ./gradlew
  echo "GRADLE_CMD=./gradlew" >> "$GITHUB_ENV"       # 仅当 gradle 缺失且 wrapper 完整时兜底
else
  echo "::error::No Gradle available ..."; exit 1
fi
```

后续所有构建步骤统一用 `"$GRADLE_CMD"`。

> 如果将来补齐了完整可用的 wrapper 并希望改回 wrapper 优先，
> 只需把上面第一个分支与第二个分支对调，**不需要改动任何构建步骤**。

### 3.2.2 模块级验证（开荒期专用）

开荒期模块是逐个落地的（`core-model` → `core-engine` → `core-agent`/`core-data` → `core-design` → `feature-*` → `app`），
在 `:app` 还不存在时跑 `:app:assembleDebug` 必然失败。

因此 `workflow_dispatch` 提供了 `gradle_task` 输入：

```bash
gh workflow run build.yml -f gradle_task=":core-model:assembleDebug"
```

- 默认 `:app:assembleDebug`；留空也走默认值。
- 输入值会被插值进 shell，因此做了**白名单校验**（只允许 `[A-Za-z0-9_:.-]`），非法值直接报错退出。
- library 模块产出的是 `.aar` 不是 `.apk`：此时跳过 APK 上传，改传 `**/build/outputs/aar/*.aar`；
  只有默认任务 `:app:assembleDebug` 没产出 APK 才算真失败。

建议每完成 1~2 个模块就用这种方式推一次 CI，别攒到最后。

### 3.3 Android SDK 许可自愈

AGP 9 会自动下载缺失的 platform / build-tools（`android.builder.sdkDownload=true`），
但**许可证未接受会让下载直接失败**。所以工作流在运行构建之前先把许可哈希写进 SDK 根目录：

```bash
mkdir -p "$sdk_root/licenses"
printf '%s\n%s\n' \
  '24333f8a63b6825ea9c5514f83c2829b004d1fee' \
  '8933bad161af4178b1185d1a37fbf41ea5269c55' \
  > "$sdk_root/licenses/android-sdk-license"
# ... android-sdk-preview-license / intel-android-extra-license / android-googletv-license
```

SDK 根目录按 `ANDROID_HOME` → `$HOME/android-sdk` → `/usr/local/lib/android/sdk` → … 顺序探测，
若镜像里带 `cmdline-tools` 再补跑一次 `sdkmanager --licenses` 兜底。

### 3.4 CI Gradle 属性

`.github/ci-gradle.properties` 被复制到 `~/.gradle/gradle.properties`。
**用户级 properties 优先级高于项目级**，所以它只放「构建环境」相关开关，不碰依赖版本与 SDK 版本：

| 键 | 值 | 取舍理由 |
|---|---|---|
| `org.gradle.jvmargs` | `-Xmx4g -XX:MaxMetaspaceSize=1g -Dfile.encoding=UTF-8` | runner 约 4 vCPU / 16 GB，留足余量给 Kotlin 编译进程 |
| `org.gradle.daemon` | `false` | CI 一次性任务，避免常驻进程与锁竞争 |
| `org.gradle.parallel` | `true` | 多模块并行；代价是日志交错，可接受 |
| `org.gradle.configuration-cache` | **`false`** | AGP 9 + Compose 编译器组合下配置缓存行为不确定；**正确性优先于几十秒速度**，稳定后可再试 |
| `org.gradle.caching` | `true` | task 级构建缓存，由 setup-gradle 持久化 |
| `kotlin.incremental` | `false` | CI 每次全新 checkout，增量无意义且偶发状态不一致 |
| `android.builder.sdkDownload` | `true` | 允许自动下载 compileSdk 36 组件 |
| `android.nonTransitiveRClass` | `true` | AGP 8+ 默认值，显式声明保证本地/CI 一致 |
| `android.nonFinalResIds` | `true` | AGP 8+ 默认值 |
| `android.useAndroidX` | `true` | 无 legacy support 依赖 |

命令行还额外传了 `-Dorg.gradle.jvmargs=...`（优先级最高），与文件同值，做双保险。

### 3.5 构建与产物

```bash
"$GRADLE_CMD" --no-daemon --stacktrace -Dorg.gradle.jvmargs=... "$GRADLE_TASK"
```

- **只跑 assembleDebug，不跑 lint / test**。开荒阶段 lint 规则不稳定，跑它会引入与「能否编译」无关的噪音。
  后续若要加 lint，应作为**独立 job** 而非塞进主构建。
- 先单独跑 `"$GRADLE_CMD" --version` 验证工具链，把「Gradle 装不起来」和「源码编译失败」两类问题分开。
- 成功后校验 APK 真实存在再上传（`if-no-files-found: error`），避免空产物被当成成功。
- 失败时上传 `**/build/reports/**`、`**/build/outputs/logs/**`，
  并额外打印 JDK 版本、SDK 已装 platform / build-tools 列表。
- **CI 绝不下载模型**：4B 模型 > 2GB，模型由用户自行导入（架构文档 §0.3）。
  工作流里没有任何拉取 `.litertlm` / `.task` 的步骤，也不要加。

## 4. `release.yml`：可选签名

### 4.1 密钥约定

四个 secrets，**全部可选**：

| Secret | 含义 | 获取方式 |
|---|---|---|
| `SIGNING_KEYSTORE_BASE64` | keystore 文件的 base64 | `openssl base64 -A -in liquidagent.jks` |
| `SIGNING_KEYSTORE_PASSWORD` | keystore 密码 | |
| `SIGNING_KEY_ALIAS` | key alias | `keytool -list -v -keystore liquidagent.jks` |
| `SIGNING_KEY_PASSWORD` | key 密码 | |

### 4.2 为什么用 step outputs 而不是 `if: secrets.X != ''`

`secrets` 上下文在步骤级 `if` 表达式中的可用性并不可靠，因此这里用 shell 探测后写入 outputs：

```yaml
- name: Detect signing secrets
  id: signing
  env:
    KS_B64: ${{ secrets.SIGNING_KEYSTORE_BASE64 }}
    # ...
  run: |
    if [ -n "${KS_B64:-}" ] && ... ; then
      echo "available=true"  >> "$GITHUB_OUTPUT"
    else
      echo "available=false" >> "$GITHUB_OUTPUT"
      echo "::notice::Signing secrets NOT configured ..."
    fi
```

后续步骤用 `if: steps.signing.outputs.available == 'true'` 做门禁。
**四个 secret 缺任何一个都整体降级**，避免出现「有 keystore 没密码」的半配置状态。

### 4.3 降级路径

```
assembleDebug          → 无条件执行，永远有一个能装的 APK
  ↓
Detect signing secrets → available=false 时：跳过 decode keystore / assembleRelease / gh-release
  ↓
Publish GitHub Release → 仅在 refs/tags/v* 且 assembleRelease 成功时执行
```

### 4.4 `-P` 属性名（**给开发同事的硬性约定**）

CI 通过 `-P` 传入：

```bash
./gradlew :app:assembleRelease \
  -Psigning.storeFile=/path/to/liquidagent-release.jks \
  -Psigning.storePassword=*** \
  -Psigning.keyAlias=*** \
  -Psigning.keyPassword=***
```

`app/build.gradle.kts` 必须实现如下逻辑：

```kotlin
// 伪代码，示意约定
val storeFilePath = project.findProperty("signing.storeFile")?.toString()
if (storeFilePath != null && File(storeFilePath).exists()) {
    signingConfigs.create("release") {
        storeFile = file(storeFilePath)
        storePassword = project.findProperty("signing.storePassword")?.toString()
        keyAlias     = project.findProperty("signing.keyAlias")?.toString()
        keyPassword  = project.findProperty("signing.keyPassword")?.toString()
    }
    buildTypes.getByName("release") { signingConfig = signingConfigs.getByName("release") }
} else {
    // 无签名配置：release 退回 debug 签名，保证 assembleRelease 仍然可跑通
}
```

要点：

1. **属性名固定为** `signing.storeFile` / `signing.storePassword` / `signing.keyAlias` / `signing.keyPassword`。
2. 用 `findProperty`（返回 `null`）而不是 `property`（缺失会抛异常）。
3. **release 构建类型必须始终存在**，只是签名配置可选——否则无密钥时 `assembleRelease` 会因找不到 build type 而失败。
4. 降档时退回 debug 签名即可，AGP 允许这种配置；产物不能上架，但 CI 能跑绿。

## 5. 排障手册

### 5.1 先做这三件事

1. 打开失败 run 的 **Annotations** 面板 —— `::error::` / `::warning::` 会直接钉在具体步骤上。
2. 下载 `build-reports-<sha>` artifact，看 `**/build/reports/**` 下的 HTML 报告。
3. 展开失败步骤的日志，找第一个 `What went wrong:`（Gradle 的真因永远在它下面，`Caused by:` 是更深层原因）。

> 不要只看最后一段日志。Gradle 的错误摘要在末尾，但真正的根因通常在
> `Execution failed for task ':app:xxx'` 之后紧跟的 `> ` 缩进块里。

### 5.2 常见失败与处理

#### A. SDK 许可 / 平台下载失败

```
Failed to install the following Android SDK packages as some licences have not been accepted.
```

或

```
Could not determine the dependencies of task ':app:compileDebugJavaWithJavac'.
> Failed to find Build Tools revision 36.x
```

**处理**：确认 `Bootstrap Android SDK and accept licenses` 步骤跑过，且 `ANDROID_HOME` 指向真实存在的目录。
如果 runner 镜像换了路径导致探测失败，在日志里看 `::notice::Android SDK root = ...` 确认。
许可证哈希若被 Google 更新，需要同步改 `build.yml` / `release.yml` 里的哈希列表。

#### B. 依赖解析失败

```
Could not resolve com.google.ai.edge.litertlm:litertlm-android:0.11.0
```

**处理**：
1. 先确认坐标与版本 —— `litertlm-android` 是 `com.google.ai.edge.litertlm` 组下的产物，
   与 `com.google.mediapipe:tasks-genai` 和 `com.google.ai.edge:litertlm` 都不同（见简报 §3）。
2. 确认 `settings.gradle.kts` 的 `dependencyResolutionManagement` 里包含 `google()` 与 `mavenCentral()`。
3. 若该版本在 Google Maven 上不可达，说明已下架 —— 需要改版本，**不要**私自升到 0.17.x，先同步给主理人。

#### C. Compose 编译器与 Kotlin 版本不匹配

```
This version (x.y.z) of the Compose Compiler requires Kotlin version a.b.c but you appear to be using Kotlin version d.e.f
```

或类似的 `IllegalArgumentException: No value passed for parameter` / 编译期崩溃。

**处理（严格按简报 §4 的降档策略，禁止提前自行改动）**：

1. **第一步：Kotlin 2.3.0 → 2.2.21**（与 gallery main 完全一致）。这是已知的高风险点：
   Compose BOM `2026.02.00` × Kotlin `2.3.0` 未在同一仓库验证过（gallery 用的是 2.2.21）。
2. **第二步（仅当第一步无效）：降 Compose BOM**，退到 gallery 验证过的版本。
3. 每一步都单独提交、单独看 CI 结果，不要一次改两个变量。

#### D. AGP 9 DSL 写法问题

```
Unresolved reference: compileSdk
```

**处理**：AGP 9.x 用块式 DSL：

```kotlin
android {
    compileSdk { version = release(36) }
}
```

简报 §4 已明确：`compileSdk 36 / targetSdk 36 / minSdk 31`。

#### E. 内存 / GC 相关

```
OutOfMemoryError / GC overhead limit exceeded / Could not reserve enough space for object heap
```

**处理**：调 `.github/ci-gradle.properties` 里的 `org.gradle.jvmargs`。
runner 是 4 vCPU / 16 GB，`-Xmx4g` 已经偏保守；如果仍 OOM，说明可能有依赖把整个模型文件读进内存，先查代码而不是继续加内存。

#### F. 配置缓存相关

```
Configuration cache state could not be cached: ...
```

**处理**：CI 已显式 `org.gradle.configuration-cache=false`。如果还在报，说明项目级 `gradle.properties`
里没有覆盖成功——检查 `Install CI Gradle properties` 步骤的 `::group::` 输出，确认文件确实写进去了。

#### G. Gradle wrapper 缺失 / 损坏

```
Could not open ... gradle-wrapper.jar
Error: Could not find or load main class org.gradle.wrapper.GradleWrapperMain
```

**处理**：CI 默认**根本不走 wrapper**（见 §3.2.1），所以这类报错意味着
`gradle/actions/setup-gradle` 没把 `gradle` 装上、导致回落到了 wrapper 兜底分支。

排查顺序：

1. 看 `Resolve Gradle launcher` 步骤的日志，确认 `GRADLE_CMD` 是 `gradle` 还是 `./gradlew`。
   正常情况下应该是 `gradle` + 一条 `::notice::Using Gradle installed by ...`。
2. 若回落到了 `./gradlew`，检查 `Set up Gradle` 步骤日志 —— 大概率是 `gradle-version: '9.7.1'`
   这个分发下载失败，或该 action 的输入名发生了变化。
3. 若确实要走 wrapper：补齐 `gradle/wrapper/gradle-wrapper.properties`
   （`distributionUrl` 指向 Gradle **9.7.1**）并确保 `gradle-wrapper.jar` 完整
   （`.gitignore` 里有 `!gradle-wrapper.jar` 显式放行）。

#### H. Action 版本无法解析

```
Unable to resolve action `actions/setup-java@v5`, unable to find version `v5`
```

**处理**：改 `.github/workflows/*.yml` 里的 tag 即可，输入参数不用动。
已知可用：`setup-java` **v5**（v5.7.0，本项目在用）与 v6；**v1–v4 上游已废弃**。
同类问题对 `actions/checkout@v4`、`gradle/actions/setup-gradle@v4`、`softprops/action-gh-release@v2` 同样适用。

#### I. 首次构建特别慢 / 超时

`litertlm-android` 是个不小的 AAR，首次构建需要下载并解压，**10 分钟量级属正常**。
`timeout-minutes: 45` 留了充足余量；后续构建命中 `setup-gradle` 的依赖缓存后会快很多。

若仍超时：看 `Set up Gradle` 的 job summary 确认缓存是否命中；
缓存未命中通常是 `gradle/libs.versions.toml` 又变了（缓存 key 与依赖版本相关）。

### 5.3 优化项（后续可做）

| 项 | 收益 | 前置条件 |
|---|---|---|
| 拆出独立的 `lint` / `test` job 并与主构建并行 | 主构建反馈更快，lint 失败不阻塞 APK 产出 | 构建稳定后 |
| 开启 `org.gradle.configuration-cache=true` | 二次构建显著提速 | AGP 9 + Compose 组合验证通过 |
| PR 上按 changed paths 过滤（非 Android 文件改动跳过构建） | 省 CI 额度 | 需要稳定的 path filter |
| 增加 `macos-latest` runner 做交叉验证 | 发现平台相关问题 | 当前 runner 时长翻倍，暂不划算 |
| 上传 APK 到 PR 评论 / 分发平台 |  reviewers 直接装包 | 需要额外 token，**零密钥约束下暂缓** |

## 6. 本地没有 JDK 也能改 CI

修改工作流后，用 CLI 触发并观察：

```bash
gh workflow run build.yml --ref <branch>
gh run watch            # 实时跟踪
gh run view --log-failed  # 只看失败步骤的日志
```

YAML 语法可以在提交前用任一 YAML 解析器粗验（CI 本身也会在解析失败时立刻报错，成本很低）。

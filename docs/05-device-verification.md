# 真机验证清单

云端 CI 只能证明代码能编译，证明不了行为正确。本轮修复的缺陷几乎全是**静默**的——
不崩溃、不报错，只是结果错。这些只有真机能验证。

按优先级排列。每一项都写明：验什么、怎么验、期望、以及出问题时去诊断页看哪类日志。

## 前置：先把诊断页摸熟

设置页 →「诊断信息」。两个分区：

- **本次运行（内存）**：本次启动以来的决策点与异常。上限 200 条，环形覆盖。
- **上次崩溃前的记录（磁盘）**：ERROR 级会落盘，重启后仍可回看。上限 50 条。

级别语义（用于判断严重性）：

| 级别 | 含义 |
|---|---|
| `INFO` | 决策点（协议判定结果、压缩触发、轮次终止） |
| `WARN` | 有异常，但我们兜住了（自动重试、闸门拦下、流式中断后补终帧） |
| `ERROR` | 已失败，用户会看到失败 |

## P0 — 模型预设数值校准（最优先）

`ModelPresets` 里 8 条预设的 `sizeBytes` 与 `requiredRamBytes` 是**手写估算值**，现在它们决定：

- `sizeBytes` → 下载前存储闸门、下载后体积提示、`sizeHint`
- `requiredRamBytes` → 加载前内存闸门

**填错的后果已降级但仍然存在**：不会删用户文件（已改为永不删除）、不会硬拦无出口（已改为警告+可继续），
但会误报提示、或该拦时过早拦。

### 怎么验

对每个预设走一遍完整流程：下载 → 观察存储/体积提示 → 加载 → 观察内存闸门行为。

记录真实值并与预设对比：

| 预设 | 预设 sizeBytes | 实测落盘大小 | 预设 requiredRamBytes | 实际加载峰值 |
|---|---|---|---|---|
| Gemma 4 E2B · GPU | | | | |
| Gemma 4 E2B · CPU | | | | |
| Gemma 4 E4B · GPU | | | | |
| Qwen2.5 1.5B · q8 | | | | |
| DeepSeek-R1 Distill Qwen 1.5B | | | | |
| MiniCPM5 2B · int4 | | | | |
| Phi-4-mini · q8 | | | | |
| LFM2.5-VL 450M | | | | |

**小模型要用小模型验**（LFM2.5-VL 450M）。它的 `requiredRamBytes` 取 2.0GB 而非按体积推算，
正是为了防「以为 512MB 模型谁都能跑」。在 1~2GB 可用内存的机器上验证它是否真能加载。

### 期望

预设值与实际偏差在合理范围；小模型不被内存闸门误放行。

## P1 — 会话水印清空后，历史是否真的重发

引擎侧用 `message.id` 做「发送水印」增量装配，会话重建时会清空水印。

**风险**：若 LiteRT-LM 原生 `Conversation` 仍保留旧 KV cache，水印清零可能导致历史被重发，
与原生历史叠加成双倍上下文。

### 怎么验

1. 开一个多轮对话，聊 5 轮以上，确保模型引用过前面的内容。
2. 中途点「停止」。
3. 继续发送新消息。

### 期望

模型记得前面的对话，且**不会**出现内容重复、自我引用、或越聊越乱。

### 出问题时

诊断页看 `INFO` 级「上下文压缩」相关记录，以及是否频繁触发压缩（上下文虚高是双倍叠加的典型表现）。

---

## P2 — 真实背景模糊的帧率

`core-design` 恢复了真实背景模糊（`BlurEffect`），此前因 API 用错被摘除。

**风险**：中低端机上掉帧。代价随「模糊半径 × 面积」增长。

### 怎么验

在**中低端机**上：

1. 聊天页滚动消息列表（多个玻璃气泡同屏）。
2. 打开对话框（顶栏/底栏等结构性玻璃）。
3. 观察是否有掉帧、卡顿、发热。

### 建议

用 Android Studio 的 FrameMetrics 或系统「GPU 呈现模式分析」采一帧。

### 出问题时

若掉帧明显，优先减少同屏玻璃数量，或给列表项（聊天气泡）关闭真实模糊——结构性玻璃（顶栏/底栏）保留即可。

---

## P3 — 上下文占用显示的准确性

聊天页输入框上方会显示「上下文 X / Y」，接近阈值时变色。

### 怎么验

多轮长对话，观察数字是否随对话增长、变色时机是否与模型开始「忘事」吻合。

**注意**：阈值复用 `AgentPolicy.compressThreshold`，所以**变色应当精确对应压缩启动**。

### 出问题时

诊断页看 `INFO` 级压缩记录。若变色与压缩不同步，说明两处阈值不一致。

---

## P4 — Gemma 4 的思考通道

`ModelFamily.GEMMA_4` 的 `thinking` 设为 **false**——模型卡暗示 Gemma 4 会产出思考内容，
但 LiteRT-LM 侧没查到思考通道依据，所以按「查不到就不设」保守关闭。

### 怎么验

用 Gemma 4 模型开启思考模式，观察是否有思考内容输出。

### 期望

若实测确实有思考内容，把 `ModelHeuristics` 里 `GEMMA_4` 的 `thinking` 改为 `true`。

---

## P5 — NPU 是否真能跑

`DeviceCapability` 提供 NPU 能力探测（`Build.SOC_MODEL` 型号数字 ≥ 8650），
且**只警告不禁用**（阈值是估计值，硬拦会误伤）。

NPU 内存系数目前是 **1.25 的保守占位**（与 GPU 相同），注释里明确标注「不是校准值，待真机校准」。

### 怎么验

1. 在支持 NPU 的骁龙 8 Gen 3+ 设备上，观察后端选择是否出现「此设备可能不支持 NPU」警告（不该出现）。
2. 选 NPU 后端加载模型。
3. 记录实际内存占用与是否成功。

### 期望

能加载则回填 NPU 的真实系数（大概率**高于** GPU 的 1.25，因为 HTP 有额外的 spill-fill scratch）。

### 出问题时

诊断页看 `ERROR` 级「引擎加载失败」——若 NPU 加载失败，切换 GPU/CPU 应能成功（引擎会自动重建重试）。

## 真机实验铁律（W72 起常驻；datastore / 日志 / 导航）

> 这一节是从 W70/W71/W72 三波「同一类事故反复发生」里提炼的**常驻 checklist**。
> 为什么进 `docs/05` 而不是只写进交接：交接是**快照**，下波不会读上波；而这几条每条都被违反过 ≥1 次。

### A. datastore 只能经 `scripts/datastore_tool.py`（⛔ 禁一次性脚本）

**事故链**：W70 首次写坏 `has_seen_intro`（切片搜索相对位置当绝对位置用）→ W71 同日恢复脚本**再踩同一坑** → 结论是「纪律重申防不住高频手工不可逆操作，必须把操作收进带护栏的工具」。

```bash
# 1) 先快照（没有快照就没有回滚锚点；工具会拒绝无快照的写入）
python scripts/datastore_tool.py snapshot --out _w72_dev/ds_pre.pb

# 2) 切激活模型（内置 UUID 对账 + 等长替换 + 补丁后自动逐字节 diff）
python scripts/datastore_tool.py set-active-model --uuid <uuid> --snap _w72_dev/ds_pre.pb

# 3) 只读比对（验证设备现状 == 某快照）
python scripts/datastore_tool.py verify --snap _w72_dev/ds_pre.pb

# 4) 还原（写回后自动再 verify）
python scripts/datastore_tool.py restore --snap _w72_dev/ds_pre.pb
```

四条护栏（缺一即 exit≠0，fail-closed）：

1. **无快照拒绝执行** —— 没有回滚锚点就不写。
2. **编译态定位** —— 只用 `re.compile(...).search(blob, ki)`（`ki = blob.find(b"active_model_id")`，`pos` 参数 = **绝对位置**）。⛔ 切片法 `search(blob[ki:])` 得到的是**相对位置**，直接当绝对位置用会写进别的字段值区 —— W70/W71 两次事故就是这个。
3. **补丁后自动逐字节 diff** —— 只允许差异**落在 UUID 跨度内**（36 字符，含 4 个连字符；实测某次切换 29 个十六进制位不同），其余任何差异即判红并自动回滚。⚠️ 判据是「**位置**在跨度内」而不是「差异字节数 == 28」—— 字节数是随两个 UUID 的十六进制相似度变化的，把它写死会误判。
4. **UUID 对账设备索引** —— uuid 必须存在于设备 `files/model_index/models.json`，否则拒绝（W70 曾把 Phi-4 的 `4d95` 写成 `4c95`，整轮"歧义"实为从未选中模型）。

⚠️ 还原后**必须逐字节 diff**，不能只查「UUID 子串存在」—— 子串在错误位置也会"通过"（W71 实例）。
⚠️ 设备真原值以设备索引为准，不以交接文档为准。

🔴 **工具缺命令时，先扩工具再实验，禁手写绕行**（W73 G2 / N-1）：要写 `set-active-model` 之外的设置位 ⇒ 先给 `scripts/datastore_tool.py` 加命令（W73 G2 范式：**字段白名单制**——白名单 = `SettingsRepository` 全部已知设置键；编译态定位 + 等长替换 + 值区 diff + 越界回滚四护栏随命令落、随单测钉），再上设备。⛔ 「就这一次」的一次性脚本 = W70/W71 三犯的共同入口（手写复活）。

### B. 日志判据：关键词必须排除「自家文案」

W72 实例：驱动脚本用 `NOT_FOUND` / `Unsupported model type` 做旗标，结果命中的是**本仓 knownBroken 预设的警告文案**（`[WARN] 激活态重校验提示：已知不可用：0.17.1 引擎初始化 NOT_FOUND（…）`），一度把「已修复」误读成「未修复」。

正确三证（缺一不判）：

1. **native / 引擎侧日志行**（`litert_lm_loader.cc` / `llm_gpu_artisan_executor.cc` 等，不是本仓 Kotlin 打印）；
2. **journal 有无 MODEL 消息**（`files/journal/<cid>/<id>.jsonl` 里 `"role":"MODEL"`）；
3. **量级佐证**（如 `tokensPerSecond`：GPU 18.3 vs CPU 0.47 ⇒ 确系 GPU 路径，不是静默回落）。

另：唯一日志文件 + 先 `pkill -f 'logcat.*<tag>'` + `logcat -c`，并按 tap 时间戳过滤陈旧行（多 nohup 叠加会让旧结论"复现"）。

### C. 导航与输入

- **发完消息先 `input keyevent 4` 收键盘**再点底部导航 tab（键盘在屏会挡住 tab，W71 二跑 `NAV_RETRY` 即此）。
- **探针/自检前必须先发一条题面把引擎加载起来**，否则 `NotRun(ENGINE_NOT_LOADED)`（W71 首跑即此坑）。⚠️ W72 起该态会额外显示已登记的坏签名，但「先加载引擎」仍是自检的前置条件。
- **生成未结束时应用会拦截页签导航** ⇒ 等 journal `settled` + 无「停止」按钮 + 页面标记验证，失败则 BACK 重试。
- **中文题面无法 `adb input text`**（非 ASCII 直接 NPE）⇒ 真机题面一律英文；中文能力靠"模型思维链仍中文"间接覆盖。
- 久置设备先 `input keyevent 224` 唤醒 + `cmd statusbar collapse` 收通知栏。

### D. 模型 UUID / 容器对账

- 设备模型清单以 `files/model_index/models.json` 为准（14 条），**脚本内 UUID 清单复用前必须对账**。
- `active_model_id` 与"某模型的 UUID"不是一回事：前者是 datastore 里的当前选择，后者是索引条目 —— 别把两者混用。

## 已知的能力边界（不必验证）

- **native 硬崩溃（SIGSEGV / OOM killer）不会产生日志**。进程直接死在推理库里，走不到 `record()`。
  日志设施只能覆盖 Kotlin 层捕获到的失败。这是能力上限，不是缺陷。
- **日志不进备份**：manifest 已设 `allowBackup="false"`，`filesDir` 不会上云。

# 真机验证清单（可勾选）

> 配套：`docs/07-fix-rationale.md`（每条改动为什么能保证理论通过）
> 用途：真机上一项一项过，判定"改动前会崩/卡/失真"的项在改动后是否真的变成正确结果。
>
> 约定：
> - **改动前**描述的是修复前代码在该场景下的表现（多数是"静默出错"而非崩溃，这是本项目的特点）；
> - **改动后期望**是判定通过的**唯一标准**，不是"看起来没崩就算过"；
> - 每测完一项在 `- [ ]` 里打 `x`，不通过的把现象填进"实测记录"。

---

## 0. 测前准备

- [ ] 确认 APK 由 `./gradlew :app:assembleDebug` 构建（CI 产物 `liquidagent-debug-<sha>`）
- [ ] 测试机至少一台 **16KB 页设备**（Android 15+ Pixel：开发者选项可切换；或用 16KB 页的模拟器系统镜像）
- [ ] 测试机至少一台**非 16KB 页设备**（用于对比，确认改动没有引入回归）
- [ ] 准备一个 **2~4GB 的 `.litertlm` 模型**（用于导入/下载路径），和一个**明显不是模型的大文件**（≥200MB，用于体积闸门）
- [ ] 准备一张 **4000×3000 原图**（相册原图即可）
- [ ] `adb shell` 可用，用于查 `dumpsys meminfo` 与 `ls` 应用目录
- [ ] 开启 `StrictMode`（若构建允许）或准备好 `adb logcat` 过滤 `StrictMode`

## 1. 启动与首启引导

### 1.1 冷启动（正常路径）
- [ ] **场景**：杀进程后重新冷启动
  - **改动前**：`bootstrap()` 三个 refresh 串行，前一个抛异常后两个不执行，且 `runCatching` 全吞无日志 → 端点列表停留在内存预设、**用户自己存的端点与 API Key 全看不见**、会话列表为空，日志里一条记录都没有
  - **改动后期望**：即使某个仓库 refresh 失败，另外两个仍会执行；失败项在应用内「诊断日志」里能看到一条 ERROR（如"端点清单加载失败（IOException）"）
  - **判定**：人为制造一次失败（见 1.2）后能看到日志，且另外两个功能仍可用

### 1.2 冷启动（`models.json` 损坏路径）
- [ ] **场景**：`adb push` 一个半截/损坏的 `models.json` 到应用文件目录，冷启动
  - **改动前**：解析失败 → 把"只剩扫描到的"写回文件 → **用户手动登记的模型永久消失，不可挽回**
  - **改动后期望**：解析失败时**一个字节都不写**，只更新内存；诊断日志出现"模型清单解析失败：已跳过回写"；手动删掉坏文件后重启能恢复正常
  - **判定**：`adb shell ls` 确认坏文件大小/内容**没被改写**

### 1.3 首启条款页（横屏 + 200% 字体）
- [ ] **场景**：横屏，系统字体调到 200%，走首启流程
  - **改动前**：`LegalStepLayout` 外层不可滚动 + 正文限高固定 300dp，横屏可用高度约 280dp →「同意并继续 / 不同意并退出」被推出屏幕 → **用户既进不去也退不出，只能杀进程**
  - **改动后期望**：页面可滚动，两个按钮都能看到并点击
  - **判定**：横屏 + 200% 字体下完成一次完整的同意流程

### 1.4 首启条款页（旋转）
- [ ] **场景**：条款页勾选同意后立即旋转屏幕
  - **改动前**：用 `rememberCoroutineScope` 落盘，旋转时协程被取消 → **可能丢掉"已同意"，TOS 页再来一遍**
  - **改动后期望**：旋转后仍停留在已同意状态，不会重来

## 2. 模型管理

### 2.1 SAF 导入大模型（正常完成）
- [ ] **场景**：模型页 → 导入本地模型 → 选一个 2~4GB 的 `.litertlm`
  - **改动前**：直接写最终名，成功即可用（这条路径原本是"能成功就没事"）
  - **改动后期望**：导入成功后模型出现在列表，大小正确，可加载
  - **判定**：能正常加载并生成

### 2.2 SAF 导入中断（关键）
- [ ] **场景**：导入进行到一半时**存储填满**或**切后台被杀**或**断开 SAF 授权**
  - **改动前**：`filesDir/models/xxx.litertlm` 留下一个 1.5GB 的半截文件；重启后被 `scanDirectories()` 扫到并登记成"正常模型" → **用户点加载 → LiteRT 解析失败 → native 崩溃闪退**
  - **改动后期望**：半截文件以 `.part` 结尾（不命中 `MODEL_EXTENSIONS`，扫描永远扫不到），或已被清理；模型列表里**不出现**任何半截条目
  - **判定**：`adb shell ls filesDir/models/` 只有 `.part` 或什么都没有；模型列表干净

### 2.3 扫描不会把异架构权重登记成模型
- [ ] **场景**：往模型目录放一个名字带 `x86` / `macos` / `gguf` 的文件
  - **改动前**：只按"扩展名 ∈ litertlm/task/bin/tflite"和"≥1MB"过滤 → 异架构权重被登记 → 点加载崩溃
  - **改动后期望**：这些文件**不被登记**（但**不删除**）
  - **判定**：模型列表无该项，且文件仍在磁盘上

### 2.4 下载过程中界面不卡
- [ ] **场景**：输入 URL 下载一个 2~4GB 模型，下载期间在模型页滚动/切换
  - **改动前**：`ModelDownloader` 四个方法阻塞 IO 且无 dispatcher，`viewModelScope`（主线程）每 200ms~1s 轮询 → **ANR 风险 + StrictMode 违规 + 页面明显卡**
  - **改动后期望**：下载期间界面流畅；`logcat` 不应出现 `StrictModeDiskReadViolation`
  - **判定**：下载全程能顺畅滚动列表

### 2.5 取消/失败下载不留孤儿文件
- [ ] **场景**：开始下载 4GB 模型，下到一半点取消（或断网让它失败）
  - **改动前**：`cancel()` 只删下载记录不删文件 → 磁盘留几 GB `.part`，DM 记录也没了，**App 里没有任何入口能再找到或删掉它**
  - **改动后期望**：取消/失败后 `.part` 被清理
  - **判定**：`adb shell ls` 对应目录无残留 `.part`

### 2.6 生成中切到模型页点加载/卸载（**P0，最重要**）
- [ ] **场景**：对话页发起一条生成（4B 模型约 50 秒）→ 底栏切「模型」→ 点某张卡的「加载」
- [ ] **场景**：同上，改点「卸载」
  - **改动前**：`ModelsViewModel` 完全绕开 `AgentRunner` 拿到同一个引擎单例；`waitForGenerationsToFinish()` 只等 5 秒且超时不放弃 → `releaseInternal()` 在 native 解码还在跑时 `engine.close()` → **SIGSEGV 闪退**。`unload()` 更危险：不查忙状态、不弹确认，一下点就是崩溃
  - **改动后期望**：**不闪退**。要么等待后完成加载/卸载，要么弹出"上一次生成仍在进行，请稍候再试"
  - **判定**：两个场景各测一次，均不崩溃

### 2.7 卸载失败不谎报成功
- [ ] **场景**：制造一次卸载失败（见 2.6，或卸载正在使用的模型）
  - **改动前**：`runCatching` 吞掉异常后仍置 `loadedModelId = null` 并提示"已卸载" → **UI 与真实状态不一致**，用户以为卸了再去点加载就是崩溃路径
  - **改动后期望**：失败时**不置** `loadedModelId = null`，提示"卸载失败"
  - **判定**：失败后 UI 状态与实际引擎状态一致

### 2.8 能力位变更后重新加载
- [ ] **场景**：加载一个 `capabilities.image = false` 的模型 → 模型页「编辑能力位」把 `image` 改成 true → 重新加载 → 发一张图
  - **改动前**：`sameEngine` 判据比较原始配置值，两种情况都判定"可复用" → **不重建引擎** → 模型被标成支持视觉、UI 允许发图，底层却没视觉后端 → **"我明明开了能力位，图片就是没反应"**
  - **改动后期望**：重新加载后视觉后端真正生效，发图有响应
  - **判定**：图片能被处理（不是报错也不是无反应）

### 2.9 改 sampling 参数后生效
- [ ] **场景**：设置页把 temperature 从 0.7 改到 0.1（或改 topK/topP）→ 回聊天页同一 prompt 连续问两次
  - **改动前**：`sameEngine` 判据不含采样参数 → 会话不重建 → **新采样参数永远进不了引擎**，反复调参输出毫无变化、无任何报错
  - **改动后期望**：temperature 0.1 与 1.5 的输出风格**有明显差异**
  - **判定**：两次输出可区分

## 3. 聊天与流式输出

### 3.1 流式输出跟随到底
- [ ] **场景**：问一个会产生长回答的问题
  - **改动前**：`ChatMessageList` 的两个 `LaunchedEffect` 分别 key 在 `messages.size` 与 `isStreaming`，流式期间两者都不变 → **整个流式期间一次都不滚动**；且 `animateScrollToItem` 把目标顶部对齐 → 气泡变高后最新内容被顶出屏幕
  - **改动后期望**：流式期间自动跟随，最新 token 始终可见
  - **判定**：全程能看到最新内容，无需手动滚动

### 3.2 本地引擎回答不重复（**仅本地推理，远程测不出**）
- [ ] **场景**：用本地 4B 模型问一个中等长度的问题，完整读一遍回答
  - **改动前**：`DeltaTracker.next()` 判据是 `>` 而非 `>=`，累积式回调遇到"与上一帧相同的帧"时 `4 > 4` 不成立 → 走增量分支 → **把同一串再拼一遍，回答大段重复**
  - **改动后期望**：回答流畅无重复
  - **判定**：通读无重复段落
  - ⚠️ **注意**：本地 LiteRT 引擎才走 `DeltaTracker`，远程端点走 OpenAI delta 协议不经这里 —— **必须测本地模型**

### 3.3 停止按钮（纯文本生成中）
- [ ] **场景**：生成中点停止
  - **改动前**：正常
  - **改动后期望**：立即停止，半截回答保留（不凭空消失）

### 3.4 停止按钮（**工具执行期间，P0**）
- [ ] **场景**：开启工具 → 问"现在几点"（触发 `current_time`）或"读一下 a.txt"（触发 `file_read`）→ **在工具执行的那段时间点停止**
  - **改动前**：`executeWithGuard()` 的 `catch (t: Throwable)` 只区分 `TimeoutCancellationException`，普通 `CancellationException` 被吞成"工具执行异常"**不上抛** → 主循环不知道该停 → `round++` → **再跑一整轮 4B 推理**（几十秒、持续烧电占 GPU），UI 显示已停，日志记成"工具异常"
  - **改动后期望**：点停止后**立即**停止，不再发起新的一轮推理
  - **判定**：`logcat` 里停止后**不再出现**下一轮 `RoundStarted`；CPU/功耗立即回落

### 3.5 工具超时仍可恢复
- [ ] **场景**：让工具执行超过 15 秒（如读一个很大的文件）
  - **改动后期望**：超时被识别为"工具执行超时"这一种**可恢复错误**，而不是把整个 run 取消（这条验证了 `TimeoutCancellationException` 必须**先于** `CancellationException` 被排除）
  - **判定**：提示工具超时，但会话仍可继续对话

### 3.6 发一张 4000×3000 原图
- [ ] **场景**：已加载 4B 模型 → 聊天页通过 SAF 选一张相册原图发送
  - **改动前**：`AttachmentBytesReader.imagePngBytes()` 无 `inSampleSize`，全量解码 48MB → 叠加模型已占的 2~3GB → **OOM 闪退**
  - **改动后期望**：不崩溃；`dumpsys meminfo` 峰值不再跳 50MB+
  - **判定**：能正常发送并得到响应

### 3.7 附件缩略图（云盘文件）
- [ ] **场景**：从**网盘 Provider**（Google Drive / 各家云盘）选一个文件作为附件
  - **改动前**：`AttachmentThumb` 在组合期同步 `openInputStream`，网盘 Provider 会主线程同步阻塞 → **ANR**；且 `inJustDecodeBounds` 失败时 `outWidth = -1` → `sample = 1` → **整图解码 24~36MB → OOM**
  - **改动后期望**：不 ANR、不 OOM；解码失败时显示占位图标而不是崩
  - **判定**：能正常显示缩略图或占位图

### 3.8 让模型读一个超大文件
- [ ] **场景**：沙箱内放一个 ≥200MB 的文件，让模型 `file_read` 它
  - **改动前**：`readText()` 全量读入再 `take(200_000)` → 200MB 文件产生约 400MB String（UTF-16）→ **OOM**
  - **改动后期望**：被体积闸门（32MB）拦下并明确提示"文件过大"，或被流式读取前 200_000 字符
  - **判定**：不崩溃，且模型知道结果可能被截断（描述里写了"输出最多 200000 字符"）

### 3.9 多工具结果都能进上下文
- [ ] **场景**：让模型在一次回复里连续调用多个工具，且触发一次上下文压缩
  - **改动前**：`buildContents()` 的 `Role.TOOL` 分支只取 `firstOrNull()` → **模型只看到第一个工具的结果**，以为其余没执行 → 反复重试
  - **改动后期望**：所有工具结果都进上下文
  - **判定**：模型不重复调用已完成的工具

### 3.10 长会话下不卡（O(n²) → O(n)）
- [ ] **场景**：`maxAgentRounds` 调到 32，关掉上下文压缩，会话累积到几百条 → 发送
  - **改动前**：每轮对整段上下文做 3 次全量扫描，且 `compress` 内贪心循环逐条再 estimate → **O(n²)**，每轮"思考停顿"明显变长，用户感知为卡住
  - **改动后期望**：每轮间隔稳定，不随会话长度明显恶化

### 3.11 上下文占用显示正确
- [ ] **场景**：长对话，观察上下文占用显示
  - **改动前**：`lastUsage` 取历史**第一条**消息的 usage，不是最近一条 → 显示的是很久以前的统计，或恒为 null
  - **改动后期望**：显示最近一次带 usage 的统计

## 4. 远程端点

### 4.1 端点名带凭据时不泄露（**P1，凭据安全**）
- [ ] **场景**：添加一个端点，**name 留空**，baseUrl 填 `https://your-proxy.example.com/v1?key=sk-xxxx` → 保存 → 加载 → 触发一次失败
  - **改动前**：`RemoteEndpoint.name` 为空时回退成 `baseUrl`，而 `OpenAiCompatibleEngine.load()` 的异常文案是 `"${remote.name} 需要填写 API Key"` → **把 `?key=sk-xxxx` 显示在用户屏幕上**，并进入截图/录屏/bug report
  - **改动后期望**：错误提示里 `key=***`（**保留参数名、只替换值**，用户还能看出是哪个参数漏了）
  - **判定**：屏幕上**看不到** `sk-xxxx` 原文
  - 对应落点：`ModelsViewModel.loadModel()`、`ChatViewModel` 三处（335/410/516）

### 4.2 远程流式期间停止
- [ ] **场景**：用远程端点生成，中途点停止
  - **改动前**：`close()` 不 cancel `activeCall` → 连接最长挂到 60 秒 readTimeout，**期间服务端仍在计费生成**
  - **改动后期望**：立即断开，服务端停止生成

### 4.3 远程引擎 tokenCount 合理
- [ ] **场景**：观察远程引擎下的 token 统计
  - **改动前**：`(text.length * 1000 / contextLength).coerceAtLeast(1)` → `"hello"` 在 32768 上下文下返回 1，**任何短文本恒为 1**
  - **改动后期望**：与本地引擎口径一致的估算值

## 5. 设置与参数

### 5.1 拖动滑块不卡
- [ ] **场景**：设置页连续拖动 temperature / topP / topK / 玻璃强度 滑块
  - **改动前**：`onValueChange` 每帧写 DataStore → 约 **60 次/秒磁盘事务**；"玻璃强度"还会触发全 App 重组 + 每个玻璃节点重画（含背景模糊录制）→ **拖动必卡**
  - **改动后期望**：拖动流畅，只在**松手时**落盘一次
  - **判定**：拖动过程无掉帧；松手后值被保存

### 5.2 非中文/非英文 Locale 下数字格式
- [ ] **场景**：系统语言切到**德语**（或阿拉伯语）→ 让模型算 `10/3`；观察各处浮点文案
  - **改动前**：`"%.2f".format(x)` 用默认 Locale → 德语区输出 `3,33`；计算器工具输出 `3,3333333333` → **模型可能把逗号当千分位或列表分隔 → 后续推理出错且无任何报错**
  - **改动后期望**：统一 `3.33` / `3.3333333333`（`Locale.US`）
  - **判定**：计算器结果与浮点文案都使用点号

### 5.3 土耳其语 Locale 下无进展检测
- [ ] **场景**：系统语言切到**土耳其语** → 让模型进入一个会重复的循环
  - **改动前**：`lowercase()` Locale 敏感，`"I".lowercase() == "ı"` → 重复检测的签名归一化不稳定 → 无进展检测失效
  - **改动后期望**：仍能检测出"无进展"并停止

### 5.4 视觉/音频后端变更触发重建
- [ ] **场景**：设置里改 vision/audio backend → 重新加载模型
  - **改动前**：属 `EngineConfig` 级参数，若只重建会话则**改了不生效**（与 2.9 同类静默失效）
  - **改动后期望**：重新加载后新后端真正生效（改这两个参数频率极低，重载几十秒是可接受且符合预期的）

## 6. 配置变更与导航

### 6.1 底栏切页后返回键直接退出
- [ ] **场景**：底栏在「对话 / 模型 / 设置」之间来回切 5 次 → 按返回键
  - **改动前**：`navigateTop()` 无 `popUpTo` → 返回栈 `[chat, models, chat, models…]` 无限累积；`NavHost` 内部 `PredictiveBackHandler(currentBackStack.size > 1)` 吃掉返回键 → **按返回变成"在上个页签间倒着走"，退出要按 N 次**
  - **改动后期望**：一次返回即退出
  - **判定**：切 5 次后一次返回退出

### 6.2 切回对话页保留状态
- [ ] **场景**：对话页输入一半草稿 + 正在流式生成 → 切到模型页 → 切回对话页
  - **改动前**：每个 `chat` backstack entry 有自己的 `ViewModelStore`，每次切回都是**全新 `ChatViewModel`** → 草稿、滚动位置、工具轨迹全丢，**正在流式生成的回答也从界面消失**（旧 VM 还在后台跑）
  - **改动后期望**：草稿、滚动位置、正在生成的回答都还在

### 6.3 三键导航下 FAB 不被遮挡
- [ ] **场景**：切到三键导航模式 → 看对话页 FAB
  - **改动前**：FAB 槽只有 `padding(end/bottom = 20.dp)` 且 `contentWindowInsets` 默认 0 → nav bar 高 48dp，**约 28dp 落在导航栏区域内**，被压住且点击易被吃掉
  - **改动后期望**：FAB 完整可见可点

### 6.4 各处输入框不被键盘遮挡
- [ ] **场景**：分别打开「参数面板」「设置页」「工具页」「端点编辑对话框」，聚焦输入框
  - **改动前**：全仓只有 `ChatInputBar` 一处有 `imePadding`；项目已 `setDecorFitsSystemWindows(false)` 走 edge-to-edge → 其余界面键盘遮挡输入框
  - **改动后期望**：输入焦点始终可见
  - ⚠️ **端点编辑对话框需特别注意**：Dialog 是独立窗口，`WindowInsets.ime` 能否生效取决于 `decorFitsSystemWindows`。修复是"无害加固"——**最坏情况是没生效，不会变坏**，但仍需实测确认

### 6.5 旋转/折叠不丢状态
- [ ] **场景**：在对话页（含 `paramsOpen` 抽屉、`listState` 滚动位置）、模型页（下载 URL 输入、删除确认对话框）、端点编辑页分别旋转屏幕
  - **改动前**：全仓只有 1 处 `rememberSaveable` → 这些状态全部丢失；`ModelDownloadCard` 的下载 URL 在 `LazyGrid` item 里 `remember`，滑回来被回收即清空
  - **改动后期望**：旋转后状态保留

## 7. 视觉与无障碍

### 7.1 浅色模式下文字可读
- [ ] **场景**：切到浅色主题，看次级文本（11sp `labelSmall`）
  - **改动前**：`onGlassSubtle = 0x66` 叠浅色玻璃后实际约 `#96969A`，**对比度仅约 2.6:1**（远低于 WCAG 4.5:1），却承担大量次级文本
  - **改动后期望**：对比度 ≥ 4.5:1（改动后理论约 6.6:1）
  - **判定**：实际观感清晰；如条件允许用取色器复核

### 7.2 浅色模式状态栏图标
- [ ] **场景**：浅色模式下看状态栏
  - **改动前**：`windowLightStatusBar = false` 且无运行时切换 → 状态栏图标是**白色**，画在浅色壁纸上几乎看不见
  - **改动后期望**：图标为深色，清晰可见

### 7.3 触摸目标 ≥ 48dp
- [ ] **场景**：依次点按 `GlassSegmented`、发送按钮、`GlassChip`、移除附件图标、错误卡关闭按钮、端点卡的编辑/删除
  - **改动前**：多数 < 48dp（项目自己的 `GlassTokens.minTouchTarget` 就是 48.dp）
  - **改动后期望**：都容易点中，误触明显减少

### 7.4 背景模糊性能
- [ ] **场景**：在有多个玻璃节点的页面上滚动 / 流式生成
  - **改动前**：每个玻璃节点每帧一次离屏录制 + `BlurEffect`（半径折算 42~120px），一屏十几个节点 × 60fps → 中低端机持续掉帧
  - **改动后期望**：设置页提供「背景模糊」开关；关闭后流畅度明显改善
  - **判定**：记录开关前后的观感差异（如需精确数据用 `adb shell dumpsys gfxinfo`）

## 8. 数据持久化与恢复

### 8.1 会话消息不丢
- [ ] **场景**：触发一次并发场景（见 3.4 停止按钮，或快速连续发送）后重新进入会话
  - **改动前**：`ConversationRepository.appendMessage()` 是 load-modify-save 无锁 → 后写的整份覆盖先写的 → **用户消息或整条 assistant 回答从历史里消失，界面上还显示着，重新进入就没了，无任何报错**
  - **改动后期望**：消息齐全
  - **判定**：退出再进入，消息数量与内容一致

### 8.2 会话不无声消失
- [ ] **场景**：连续保存多个会话，期间人为杀进程（模拟 LMK）
  - **改动前**：`save()` 先写 `<id>.json` 再写 `index.json`，两次写之间被杀 → `index.json` 里没有这个会话但全文文件在 → **用户在列表页看不到刚聊的会话（无声丢失）**
  - **改动后期望**：最坏情况是"列表有一条、点进去是空的"（用户可见、可重建），而不是"列表里根本没有"

### 8.3 端点不丢
- [ ] **场景**：设置页快速连续保存两个端点
  - **改动前**：`upsert()` 是 read-modify-write 无锁 → 其中一个条目被覆盖丢失
  - **改动后期望**：两个端点都在

### 8.4 崩溃后诊断日志还在
- [ ] **场景**：制造一次崩溃（如 2.6 之前的行为），重启后看应用内「诊断日志」
  - **改动前**：`AgentLogFileStore.append()` 无锁，并发写会**撕行** → 两条日志交织成一行 → 两条都 parse 失败 → **崩溃现场记录丢失，恰好是本类唯一要保住的东西**；且高频 INFO 会把 WARN/ERROR 挤出 200 条缓冲
  - **改动后期望**：ERROR 记录完整可读，不被 INFO 挤掉

## 9. 兼容性与平台专项（**最高优先级**）

### 9.1 16KB 页设备（**本轮唯一的未决理论问题**）
- [ ] **场景**：在 16KB 页设备上加载模型并生成
  - **背景**：我下载 `litertlm-android-0.11.0.aar` 解析 ELF 程序头实测——三个 `.so` 的 `PT_LOAD p_align` **全是 0x4000（16384），按 Google 官方标准合规**，`vaddr % 16K == offset % 16K` 也全部成立；但 `liblitertlm_jni.so` 的 `PT_GNU_RELRO` 末端 `0xe9d000 % 16K = 4096` **未按 16KB 对齐**（另两个库都对齐）
  - **改动前/后**：本项目未改版本，行为不变。**这条是纯验证项**
  - **判定**：
    - 若正常生成 → 该差异不致命，记为已知差异，保持现状
    - 若崩溃 → **需要动 LiteRT-LM 版本目录**（届时需单独授权，因为这会打破"禁止改版本目录"的约束）
  - **取证脚本**：`.audit/elf_check.py` 可复用

### 9.2 `temperature = 0` 的真实语义
- [ ] **场景**：把 temperature 拖到 0，同一 prompt 连跑两次
  - **背景**：我们现在把 0 钳到 `0.01`；按 HF/llama.cpp 语义 `temperature <= 0` 才是贪心（确定性），`0.01` 是"极低温采样"仍带随机性。官方 gallery 直接把 slider 的 `0.0` 原样传给 `SamplerConfig`，不做钳制
  - **判定**：
    - 若两次输出**完全一致** → LiteRT 内部已做贪心 → **应去掉 `coerceAtLeast(0.01)`** 以恢复贪心语义
    - 若出现 NaN 或崩溃 → 保留钳制，并记录实测机型
  - 当前代码里已把"未验证"写进注释，**逻辑未动**

### 9.3 非 16KB 页设备回归
- [ ] **场景**：在一台普通 4KB 页设备上跑一遍 2.6 / 3.2 / 3.6
  - **目的**：确认 16KB 相关判断没有影响常规设备

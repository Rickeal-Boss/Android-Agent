## L1. 真机矩阵只有一台设备：OPPO PDRM00 / Android 13（SDK 33）

- **现象**：全部真机判据（T1–T8、K1–K8、L3 多模态、冻结实测、TTFT 分布）都取自
  **OPPO PDRM00 / ColorOS / Android 13（SDK 33）** 这一处。其他 OEM（小米 / vivo / 荣耀 / 三星 /
  原生 AOSP）、其他 Android 版本（14 / 15 / 16）**零真机数据**。
- **影响**：**任何「OEM 通用」的结论都不成立**。最具体的后果是 L3（灭屏冻结）—— ColorOS 的
  cgroup 冻结行为被实测为不可对抗，但**别家 OEM 的冻结机制与阈值我们没测过**，
  既不能外推「都一样」也不能外推「别家更好」。
- **为什么首版不做**：9 族 OEM 真机取证需要 9 台设备 + 一轮一轮的 adb 窗口，是**设备资源**问题，
  不是工程问题。首版把「已验证面」和「未验证面」划清界限（而不是假装覆盖了），比铺开 9 台更有价值。
- **台账 id**：`W78-01` / `W78-02` / `W78-03` / `W78-04`（9 族 OEM 真机取证 / FLYME 加锁 /
  OriginOS 冻结层 / 小米 PowerKeeper 探针，均 `parked` 待设备）。
- **重启前提**：拿到第二台不同 OEM 的设备（且该设备的冻结/后台机制与本仓现有取证工具链兼容）。

## L2. 冷启首字延迟 p50 ≈ 13 秒

- **现象**：历史 TTFT **p50 = 12.9s / p99 = 181s / max = 200.0s**（W82 全量 186 个会话取证）。
  这 13 秒**不是 prefill 慢**，而是**进程冷启后首个 run 的模型加载**（1.5B q8 档 / 6GB 内存设备）。
  用户感知 = 「打开 App 问第一句，等 20 秒」。
- **影响**：首屏体验受限于端侧模型加载的物理成本。中低端设备上尤其明显；内存越紧、加载越慢
  （换页 + 反序列化）。**这不是 bug，是端侧推理的固有代价** —— 云端方案没有这一项，代价是数据出设备。
- **为什么首版不做**：三条候选路都有真实代价，且**用户已裁决走保守支**：
  - A「启动即预热」= 常驻内存 + 冷启 CPU 争抢，与 `reportFullyDrawn` 664ms 的首屏目标直接冲突；
  - B「进对话页且存在 active 模型时后台预热」= 用户可能根本不发消息，白付一次加载；
  - **C「维持现状 + UI 文案披露『正在加载模型…』」= 零行为改动**（W83-08 已承接文案）。
- **台账 id**：`W82-15`（**`closed-dead`**，W86 §D 自动收敛：自 W83 起四波零裁决 > N=3 ⇒ 走保守支 C）。
- **重启前提**：产品裁决改选 A 或 B。**用户裁决优先于自动收敛**，随时可救回（转 `active` 并选 A/B）。

## L3. 国产 OEM 灭屏后进程被 cgroup 冻结 —— FGS + WakeLock + 电池豁免**均不能对抗**

- **现象**：ColorOS 灭屏后 **~10–11 秒**，`OplusHansManager` 走
  `SM_EVENT_LCD_OFF_UNIFIED_FREEZE` → `freeze uid: <pid>` → netlink `FROZEN_TRANS` 到内核
  （**cgroup 级**冻结，实测一次冻 **416 秒**）。**锁被强制回收的时刻 = 进程被冻结的时刻（同一毫秒）**。
  六项控制变量逐一实测（W78 四轮受控 + 两个对照臂），**全部无效**：
  ① FGS（`isForeground=true` / `foregroundId=1002` / `specialUse` + subtype）
  ② WakeLock（390s 超时 + 120s 周期续期）
  ③ AOSP 电池优化豁免
  ④ ColorOS「允许完全后台行为」（截图证实 ON，**仍冻**）
  ⑤ 进程新旧（`am force-stop` 冷启新 pid 复测）
  ⑥ 飞行模式开关（开/关各一轮）
  ⇒ **FGS + WakeLock + 续期是必要不充分条件。**
- **影响**：**后台长任务在国产 OEM 上不可靠**。具体后果：灭屏期间协程不执行 ⇒ 长 run 的实际耗时
  被冻结窗口拉长（同题面同设备实测 TTFT **9.8s vs 462.4s = 47 倍**，差异只在是否落进冻结窗口）。
  已做的缓解是**冻结感知超时**（`FreezeClock` 把灭屏累计从超时预算里剔除 ⇒ 解冻后继续生成、
  **不误掐**），但那是「不误杀」，**不是「冻结期间继续跑」**。
- **为什么首版不做**：**这是操作系统层的进程调度，应用侧没有对抗手段** —— W78 已把「降低被冻概率」
  与「冻结后续命」分开：后者在 ColorOS 上物理不可行（cgroup 级冻结不认应用侧任何信号）。
  首版取「如实披露 + 不误掐」而非「假装后台常驻」。
- **台账 id**：`W78-08`（硬上限判据，`active`，重启前提 = 出现可降低被冻概率的候选）、
  `W78-09`（三开关组合豁免 —— **已证伪** `closed-done`：四开关全开仍被冻）、
  `W78-12`（冻结感知超时，`closed-done`）。
- **重启前提**：拿到「系统级白名单 / 免冻结」的官方接口（目前未发现），或目标设备换成不实施
  cgroup 冻结的 OEM/ROM。

## L4. `Qwen2.5 1.5B · q8` 预设**没有** sha256 锚点（显式 fail-open）

- **现象**：14 条预设中 **13 条**的 sha256 锚点已通电；`Qwen2.5 1.5B · q8` 的
  `ModelPresets.sha256` **刻意留 `null`**。原因：该条 `sizeBytes = 1597931520`，而 ModelScope
  同名文件实测 **1597922856**（差 **8664 字节**）⇒ **「仓库体积逐字节相等」这个跨源同一性代理判据不成立**，
  无法证明镜像与预设指向同一份字节。
- **影响**：这一条预设的下载**不做摘要校验**（走 `UNREADABLE` 式的放行路径），
  即「下载到的文件是坏的」这一失败面在该条上**只能靠引擎加载失败暴露**，不能靠校验提前拦。
  其余 13 条不受影响。
- **为什么首版不做**：两条硬约束 ——
  ① 硬填一个未验证的摘要会让**主源下载被误拒**（用户下 2GB 后被拒，比不校验更糟）；
  ② 本仓沙箱**无法直连 HuggingFace**（502），拿不到 HF 侧官方摘要做第三方核对。
  ⇒ 选择**显式 fail-open + 留痕**，而不是「凑一个看起来完整的 14/14」。**「14/14」的目标被实测修正为「13/14 + 1 条例外留痕」。**
- **台账 id**：`W86-09`（`parked`，两条遗留：① 该条锚点复核；② 已下载模型摘要落库供跨 session 复用）。
- **重启前提**：能直连 HF 取到官方摘要（或该条在 ModelScope 的镜像体积与预设对齐）。
  通道已备：`scripts/fetch-preset-sha256.py` 可一键复核/回填。

## L5. 首版**仅中文**（i18n 不做）

- **现象**：`app/src/main/res/values/strings.xml` **只有 4 行**（XML 声明 + `resources` 开闭 + 1 条 `app_name`），
  而 `*/src/main` 下含中文的字符串字面量实测 **1949 处**（口径：`grep -oP '"[^"]*[\x{4e00}-\x{9fff}][^"]*"'` 的出现次数，2026-10-27 实测）。
  UI 文案、错误提示、工具描述、提示词全部**硬编码中文**。
- **影响**：非中文用户无法使用。且 `android:supportsRtl` 已在 Wave 32 **主动撤下** ——
  RTL 布局从未被验证，声明未验证过的能力比不声明更糟。
- **为什么首版不做**：i18n 不是「把中文抽到 strings.xml」这一件事，而是三件：① 抽串（~1.9k 处）；
  ② 补 `values-ldrtl` 与布局镜像；③ **真机或预览逐语言验证**。第 ③ 项需要母语审读，是**人的工作**，
  首版没有这个带宽。⇒ 先不声明（撤 `supportsRtl`），而不是声明了不验证。
- **台账 id**：**无独立台账 id** —— 登记在 README 挂账台账「完整 i18n（含 RTL）」条
  + [`docs/14-user-actions.md`](14-user-actions.md) §E9（沿袭滚动项）。
- **重启前提**：① 硬编码串抽到 `strings.xml`；② 补 `values-ldrtl` / 布局镜像的真机或预览验证；
  ③ 验证通过后才恢复 `android:supportsRtl="true"` 声明。

## L6. 无障碍未做（语义标签 / 触控目标）

- **现象**：全仓 `contentDescription =` **66 处**、`semantics {}` **4 处**（`*/src/main`，2026-10-27 实测），
  **无系统性覆盖**；48dp 最小触控目标未逐控件核对；**无 TalkBack 遍历取证**。
  玻璃卡片（`GlassCard`）是 Compose 自绘节点，`uiautomator dump` 对其下半区**零捕获**
  ⇒ 连自动化取证通道都不通。
- **影响**：视障用户无法可靠操作；屏幕阅读器读到的语义是残缺的、局部的。
- **为什么首版不做**：这是**设计系统层**的横切面，不是散点修补 —— 要么在 `core-design` 一次性定义
  语义规范并回灌全部组件，要么做了也是补丁叠补丁。首版把它整体推迟到一个专门的 `core-design` 波。
  ⚠️ **路线图 M8 里的这条 checkbox 不删**（此承诺不删，只给出账目指针）。
- **台账 id**：`W84-13`（`parked`，重启前提 = core-design 波）。
- **重启前提**：立项 `core-design` 无障碍波（含语义规范 + 48dp 触控目标 + TalkBack 真机遍历）。

## L7. `litertlm` 仍 pin **0.17.1**（bump 0.18.0 未裁决）

- **现象**：`gradle/libs.versions.toml` 的 `litertlm` 保持 **0.17.1**，由守卫 **#29** 机械钉死
  （改版本必须同时改守卫并复核 bump 前置，**bump 从「改一行 toml 静默发生」变成显式动作**）。
  0.18.0 的收益与代价**均已真机实测**（W72 条件真机臂），但**决策未拍**。
- **影响**：0.18.0 能修的两项（`gemma-4-E2B-it-gpu` 引擎初始化 `NOT_FOUND` → `GPU_ARTISAN` 18.34 tok/s；
  `MiniCPM-V-4-int8` 可建会话）**用不上**；GPU 用户故事与 MiniCPM-V-4 在 0.17.1 下继续不可用。
  同时 0.18.0 的代价也真实：**删除了「1 元素 text 数组 → string」收敛点** ⇒ `Qwen2.5-1.5B`（默认中文模型）
  与 `MiniCPM5-2B`（主推）**首轮必炸**（≥2/14 预设，`+ operator on unsupported types string and sequence`）。
- **为什么首版不做**：代价/收益严重不对称 —— 0.18.0 的两项收益都是**边缘可用**
  （E2B·GPU 输出仍退化 = 实际不可用；MiniCPM-V-4 首 token **81.8s** = 体验不可接受），
  而代价命中的是**默认锚模型的首轮 P0**。且 bump **不是改一行 toml**：五处联动
  （toml + 2 文件 API 迁移 + 守卫 #29 期望值 + `appliesToRuntime` 字面量 + `docs/12` 锚 #14）。
- **台账 id**：`W68-06`（bump 首跑判据，`active` blocker，W71 起**单维持** = 锚 #1 收敛缺失）+
  [`docs/14-user-actions.md`](14-user-actions.md) §C6 / §E6（三选项与实测数据全在案）。
- **重启前提**：上游恢复「单元素 text 数组 → string」收敛（或提供兼容开关）；
  或 app 侧落地「导入期模板数组安全性探测闸门」且该闸门产品化（含存量 14 预设取证 harness 随包分发）。

## L8. 横屏下屏幕挖孔区留黑边（`windowLayoutInDisplayCutoutMode` 保持默认）

- **现象**：横屏（`ROTATION_90/270`）时，挖孔侧留下约 **107px（≈36dp）黑边** ——
  实测 `dumpsys window displays` 的 `mAppBounds=Rect(107, 0 - 2400, 1032)`，
  窗口本身就不铺到挖孔区。竖屏不受影响（挖孔在状态栏内，被 `statusBarsPadding` 吸收）。
- **影响**：横屏可用宽度少 36dp（764dp 而非 800dp）；观感上左侧有一条黑带。
  **不影响可点性** —— Rail 与各屏内容都落在 `safeDrawing` 内。
- **为什么首版不做**：改成 `shortEdges` 会让**整窗**铺到挖孔下，于是每一屏都必须自己用
  `safeDrawing`（或 `displayCutout`）做**横向**避让；而当前多数屏只挂了 `statusBarsPadding`
  （竖屏语义：只避让顶部），横屏会直接把内容送到摄像头下面。这是一次**全屏审计**，
  不是一行主题属性 —— 收尾期不做，避免「为了 36dp 引入一类新的遮挡缺陷」。
- **台账 id**：`W88-04`（本波把该项**显式登记为不做**，不是遗漏）。
- **重启前提**：有一次专门的横屏/折叠屏设备窗口，可逐屏核对横向 `safeDrawing` 后再改。

### 本波的一处真实风险与修正（重要教训）
I1 初版实现的**检索评分阶梯**（`300/140/100/40`、逐词项 `40/16/12`、`DEFAULT_LIMIT=8`）
与参考实现**逐个数值相同**，而 KDoc 却自称「权重均为本方自拟」—— **自述与事实不符**。
独立复核抓出后已全部重推：

- 新权重按**本方语料独立推导**并写明理由：工具名是短英文标识 ⇒ 名称匹配权重最高
  （200/90）；描述是中文长句、含任意查询词概率高（噪音大）⇒ 只给 60；分类只有个位数
  取值 ⇒ 只给 25。`DEFAULT_LIMIT` 改为 6，按「单次回灌不超过 ~600 字符」反推。
- **教训**：「排序思路」属通用检索常识可自由使用，但**具体魔数**一旦逐个相同就构成
  可指摘的相似性。以后再从参考实现获得灵感，必须**重新推导数值**并写下推导依据，
  而不是复述记忆里的数字。

## 3. 深挖发现（四维度）

### R1 记忆与上下文
- **记忆 pull 化（最有价值，本波未落）**：参考实现把长期记忆**移出系统提示词**、改为
  模型主动拉取。这正面命中我方已知痛点 —— 记忆段 push 进系统提示词 ⇒ 记忆一变
  `systemText` 就变 ⇒ 引擎会话重建 ⇒ **一次全量 re-prefill**（Wave 24 记录的 P1 残留）。
  这是**结构性**问题，不是可调参数。
  **本波不做的理由**：pull 化会让小模型可能完全不查记忆（记忆功能实际失效），属行为
  回归，必须真机验证「小模型会不会主动查」。已列入路线图与真机清单。
- 摘要检查点持久化、`PromptSectionProvider` 契约建议（与 R4 合流，见 §5）。

### R2 UI 与工程治理
- **纠正我方假设**：并非「完全没有上下文可视化」—— 已有 `ChatContextMeter`。避免了一次
  重复建设。
- 最高价值项：**arch-guard 自测网**（我方 11 项守卫是纯 bash、无自带测试；对方 CI 门禁
  脚本自带单测）、**工具卡详情弹窗**（真实缺陷：内容超出即永久不可见）。
- 补充：提示词分段预览契约需两个非显然字段 `emptyReason` / `affectsSessionRebuild`；
  预览必须渲染**运行时同一份**装配结果，否则是另一种谎言。

### R3 引擎与容错
- **反直觉结论：我方在若干处强于参考实现** —— 会话重建判据、取消语义、采样档案
  （按模型给安全区间）都比对方完整。不要盲目照搬。
- 最高性价比迁移：接入 litertlm 原生 `Capabilities.defaultSamplerParams()` 作为
  `ModelSamplingProfiles` 的缺省兜底/校验（我方目前是纯手写常量）。
- 我方确实缺：模型资产 sha256 校验、native crash 兜底（**双方皆无**，不做）。

### R4 提示词工程结构
- 参考实现把提示词当一等公民（9000+ 行），但我方规模（12 工具、单语言、无用户自定义
  模板）下 **5 段硬编码是正确复杂度** —— 引入段落注册表只增加间接层。
- 两个小改：护栏位置不变量单测（需先把分段逻辑抽到 core-model 才能测，留到下一波）；
  `toPromptLine` 补参数描述（**须在 I1 之后评估**，否则描述变长会抵消披露收益）。

## 4. 本波落地：渐进式工具披露（I1）

### 4.1 设计
参考实现用「CLI 工具模式」解决「工具太多塞不下」：本地小模型只暴露 `search` + `proxy`
两个元工具，真实工具按需检索后转发。本波据其**思想**裁剪移植：

- `ToolDisclosureMode { FULL, ON_DEMAND }`，**默认 FULL = 零行为回归**。
- `HiddenToolCatalog`（core-model）：隐藏目录 + 关键词评分检索。放 core-model 的理由与
  `StreamRepetitionDetector` 相同 —— 纯逻辑可在 JVM 直接单测。
- `DisclosureTools`：两个元工具契约 + `unpackCall` 解包 + 协议说明段。
  **元工具不做成 Tool 实例**，由 AgentRunner 执行路径特判 —— 因为 `call_tool` 的语义是
  「转发」，而审批/守卫/超时/并发闸门全挂在执行路径上；做成普通 Tool 要么绕开闸门
  （安全缺口），要么复制执行路径（两处漂移源）。

### 4.2 关键性质（改这里必须复核）
1. **披露面收窄在三个消费点自动一致**：`availableTools` 换成两个元工具 spec 后，
   ① 系统提示词工具段、② 原生通道 tools、③ `TextToolProtocol` 白名单**同时**收窄。
   ③ 是关键 —— 模型**在协议层就无法直接调用隐藏工具**（未注册名降级为最终答案）。
2. **转发复用完整闸门**：解包后**换名继续走原路径**，审批判定（静态标志 ∪ 参数门控 ∪
   效果声明 ∪ 能力档位）作用在**目标工具**上 ⇒ 不构成权限旁路。审批缓存 key 用目标名 +
   目标参数 ⇒ 「授权过 A」在两条路径上语义一致。
3. **元工具声明 `effect = READ` 是跨模块契约**：转发分支必须对目标重新求值，否则 READ
   会变成「转发通道对能力档位永久隐身」。KDoc 已写明。

### 4.3 独立复核发现并修正的 8 项
| 级别 | 问题 | 修法 |
|---|---|---|
| **高** | 可用性判定用 `toolRegistry.get()` 查存在性 ⇒ ON_DEMAND 下注册表仍有全部真实工具，原生通道回吐真实名会被直接执行 | 改为先判 `call.name in registeredToolNames` 再查 registry（顺带封住「toolNames 白名单在原生通道被绕过」的既有缺口） |
| **高** | 子代理未继承披露模式 ⇒ 子 run 白名单取全量注册表，隐藏面整个还原 | `ParentContext` 加 `disclosureMode`，AgentRunner 下发 |
| 中 | `search_tools` 分支在 `continue` 早于 `toolCallStreak` 更新 ⇒ 同一 query 反复搜绕过 Wave 22 硬护栏 | 分支挪到同参签名与硬护栏之后 |
| 中 | ON_DEMAND 下报「未注册的工具」会误导（模型刚检索到的名字是对的） | 按模式给不同可行动文案 |
| 中 | 零单测 | 已补 43 用例（复核时尚未写，本轮已补） |
| 低 | `unpackCall` 参数别名少 `parameters`/`input`，与 `TextToolProtocol` 不同口径 | 补齐别名集 |
| 低 | 空目录下披露只会教模型去检索不存在的工具 | `disclosureActive` 追加 `allToolSpecs.isNotEmpty()` |
| 低 | 元工具 effect 契约缺交叉引用 | KDoc 写明跨模块契约 |

### 4.4 已核验的边界
- 新增 `DISCLOSURE_GUIDE` 是独立 section 且不以记忆前缀开头 ⇒ **会进 echoCorpus**，
  模型复述协议说明会被判定⑥/⑨ 正确拦截。
- **预算诚实性**：独立估算表明 12 个工具的规模下按需披露**未必更省 token**（元工具说明 +
  检索回灌可能超过直接列清单），临界点约在几十个工具量级。真实收益是「提示词面积与工具
  数量解耦」+「被逐字复述的面积缩小」。**设置页文案已按此修正，不承诺省上下文** ——
  对用户承诺一个我们自己没把握的收益，比不说更糟。
- 已知边界（非问题）：隐藏工具的描述只在检索回灌结果里（TOOL 消息），不在系统提示词，
  故「逐字复述工具描述」不被 ⑥/⑨ 拦。但复述一次工具结果是**正常行为**（引用工具输出），
  真循环会被判定①/⑦ 拦住，不需要额外处理。

## 5. 明确不做（附理由，别再重复调研）

| 项 | 理由 |
|---|---|
| 提示词组装管线 / 段落注册表 | 12 工具 + 单语言 + 无自定义模板的规模下，5 段硬编码是正确复杂度（R4 结论） |
| 记忆 pull 化 | 行为回归风险：小模型可能完全不查记忆 ⇒ 记忆功能实际失效。须真机验证 |
| 向量检索 / 图谱记忆 / 多记忆空间 | 无向量库、禁止新依赖；端侧收益不明 |
| 嵌入式 JS 引擎 / 工作流画布 / 统一市场 | 需 NDK/后端，与规模不匹配（Wave 26 已裁定） |
| 本地 STDIO MCP | Android 应用进程无 `exec` |
| 远程 HTTP MCP | 会打破现有「无外发通道」的 I/O 边界承诺，须先过安全评审 |
| native crash 兜底 | **双方皆无**；litertlm 崩进程是平台限制，非本仓可解 |
| 内置 Ubuntu / PRoot / 切换推理引擎 | 体积与复杂度不可接受（已定 litertlm） |

## 7. 真机验收清单（CI 查不出）

1. **零回归**：默认 FULL 档下，工具调用行为与 Wave 26 完全一致。
2. **基本链路**：切 ON_DEMAND 后，模型应能「先 search_tools 检索 → 再 call_tool 转发」；
   若模型直接猜工具名，应收到「不能直接调用，请先检索再转发」的可行动提示而非死循环。
3. **安全回归（最重要）**：ON_DEMAND × **只读档**下，让模型「用 call_tool 写文件」——
   必须照常弹授权卡（验证转发通道没有对能力档位隐身）。
4. **子代理继承**：ON_DEMAND 下触发一次 `ask_actor`，确认子 run 的系统提示词**不含**
   完整工具清单（日志或提示词预览可见）。
5. **同参护栏**：让模型用同一 query 连续 search 6 次以上，应从第 N 次起收到「已忽略未执行」。
6. **预算实测**：在 ON_DEMAND 下观察实际提示词长度与轮次，验证「工具少时未必更省」的判断
   （若明显更贵，考虑把临界工具数写进设置页文案）。
